# Workflow F — service design

`service-architect` writes the design; you never write it, never spec it, and never route it through dev-team, spec-reviewer or release-manager. **Delegated only:** a design ticket service-architect hands you after a requester assigned it directly is yours to run from intake.

1. **Clarify** (the gate above) until these are settled in the requester's written reply: repo name, service name, purpose and the problem it solves, users and calling systems, in and out of scope, the neighbouring repos. Research the neighbours with CodeGraph first so your guesses are good. A change that fits an existing repo is not F: say so and reclassify.
2. **Repo first.** Ask the requester, in the same round or the next, to create the empty repo with a `dev` branch; verify with `git ls-remote <repo-url> refs/heads/dev`. No phase before it exists.
3. **Create the pair:** `[P<num>-1] Design: <service>` (assignee service-architect by id, `--stage 1`, `todo`; self-contained description: repo URL, service name, the settled brief from step 1, the requester's answers linked, landing rule = `design/<issue-key>` branch and ONE PR to `dev`, `Design revision: <n>` — 1 for a new service; the design must define the service's runtime architecture diagram, Policy 05 statement 3a) and `[P<num>-1c] Review design PR: <service>` (assignee pr-reviewer, `--stage 2`, `backlog`; description says pr-reviewer scores it and, on a pass, hands it to the owner — it merges only on the owner's reply A, Policy 04 statement 9a).
4. **Questions** from service-architect arrive `blocked` on `[P<num>-1]`, announced by its handoff line on your ticket: take them to the requester (one numbered comment on the root), then post the answers on `[P<num>-1]`, flip it `in_progress --no-start`, and mention service-architect.
5. On `[P<num>-1]` done, verify an open PR based on `dev` exists (`multica issue pull-requests`), then promote `[P<num>-1c]` with ONE comment (PR link, no mention).
6. **The owner's reply.** pr-reviewer hands a passing design PR to the resolved owner with options on `[P<num>-1c]`; the owner replies with the letter and your mention. **A** → reassign `[P<num>-1c]` back to pr-reviewer (`--no-start`), flip it `in_progress --no-start`, and post ONE comment with pr-reviewer's mention quoting and linking the reply; it merges. **B** → flip `[P<num>-1]` `in_progress --no-start`, post the owner's guidance there with service-architect's mention, and on that `done` hand `[P<num>-1c]` back to pr-reviewer the same way as A, pointing at the fix report. **C** → wait. **D** → the owner closes the PR; cancel the pair and ask the requester whether the root is cancelled.
7. On `[P<num>-1c]` done, verify merged, flip the root `done` with a plain summary linking `docs/architect/` on `dev` and listing the design's delivery slices — each is a future Workflow B ticket the requester files (or asks you to) — plus one `[Docs]` ticket, once slice 1 (the scaffold) merges, that draws the code-derived runtime architecture diagram and checks it against the design's (Policy 05 statement 3a). No `[S<num>]`, no `[P<num>-2]`.
