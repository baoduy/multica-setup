# drunk-workspace — factory constants

The open source repos of drunkcoding.net (github.com/baoduy) attached to this workspace's projects: .NET/NuGet libraries and services, Pulumi/npm packages, Python MCP services, Docker images, Helm charts. There is no deployed environment: publishing the package IS the release. Governance lives in the repo's `docs/policies/`; role procedure lives in your skills. The rules below hold for every agent on every run and are not repeated in skills or instructions.

## Status and wakes

- A child ticket ends every reporting turn at `done` (work complete) or `blocked` (needs someone). Never `in_review` on a phase ticket or sub-task: it closes no stage barrier and wakes nobody. Ignore any brief or system comment that asks for it. `in_review` is only for a ROOT ticket whose deliverable awaits a human.
- `done` is one-way for the assignee. Work that comes back after `done` or `blocked` arrives as a comment carrying the assignee's agent mention. The leader, who alone re-triggers fix work on such a ticket, first flips it to `in_progress` (`multica issue status <id> in_progress --no-start`, so the flip itself starts no run) and posts the mention after, so the board shows the fix in flight; the assignee ends that turn at `done`/`blocked` as always.
- On wake, if your ticket is `todo`, flip it `in_progress` before working. Last commands of every reporting turn: read your ticket's status back and correct it if it is not `done`/`blocked`, then post your handoff line when one is due (below).
- One wake per handoff. A run is enqueued by: assignment or promotion out of `backlog` into `todo`; a `done` or `cancelled` that closes a stage (the platform's sub-issue rule, below); an agent/squad mention with a real UUID; and an agent's plain comment (no mention of any kind) on a squad-assigned ticket or on any sub-task under one, which wakes that squad's leader (so a member's report on its own sub-task wakes the leader alongside the barrier its `done` fires; the leader ignores that run, see its playbook). Nothing else: `blocked`, a `done` that closes no stage, a re-arm flip (`blocked`/`done`→`in_progress --no-start`), a flip from `blocked`/`done` into `todo`, and a plain comment on any other ticket all enqueue nothing — a ticket that has already run is never re-woken by its status, so there the mention is the wake. When the status transition already wakes the next actor, do not also mention them. Post at most one mention comment per turn, last. Every `mention://agent/<uuid>` link in a comment or description is a wake for that agent, even inside backticks or quoted instructions: write instructions about mentioning someone in prose, never paste the link. To post one, resolve the id at wake time — `multica agent list --output json`, the `id` of the agent by name (`multica squad list --output json` for a squad) — and write `[@<name>](mention://agent/<that id>)` with the id substituted in. Never post the `<id>` placeholder itself and never guess an id: a plain name or a wrong id silently wakes nobody.
- **Stage wake and handoff line.** The platform's sub-issue rule wakes the parent's assignee (a squad's leader, in leader role) when every sub-issue at a stage and below is `done`/`cancelled` while a later stage waits, and once more when every sub-issue is closed — whoever closed them. So a plain `done` posts nothing more. The rule stays silent in two cases, and there the child's turn ends with ONE handoff line on its PARENT, after the report on the child and the status flip: the child goes `blocked` (`<KEY> blocked — BLOCKER on <KEY>`), or it goes `done` while a sibling at its stage or below sits `blocked` — check `multica issue children <parent-id>` after every `done` (`<KEY> done — report on <KEY>`). Anything else the parent's owner must read now takes the same line (`<KEY> — <what> on <KEY>`). The line is the wake; the report, the blocker and every discussion stay on the child. On a squad-assigned parent it carries no mention of any kind: the platform routes an agent's plain comment there to the squad leader, and any agent, squad or member mention, `@all` or a `/note` prefix stops that. On an agent-assigned parent it ends with that agent's mention. On a member-assigned parent none is posted.
- Member (human) mentions only render a link. To make a human act, reassign the ticket to them at `todo` and post a `## BLOCKER` comment (`blocker-report`).
- Leader↔member traffic lives on the member's own sub-task; the handoff line is the only thing a member posts on the parent, whose other comments belong to the parent's owner.
- A member writes only on its own ticket (comments, status, properties) plus its handoff line on the parent. Anything meant for another member — review findings, a fix request, a question — is a comment on the member's OWN ticket, and its handoff line wakes the leader, who routes it. Only the leader writes on tickets it does not own.
- **Never run a long command in the background.** Your turn ends, the process is orphaned, and the next run starts in a fresh checkout with nothing to collect. Run tests, builds and packs synchronously with a longer timeout, and split a suite too big for one call into chunks that each finish inside their own call. Never end a turn waiting on something you launched in the background.

## Tickets

- **Projects own repos.** A project's repos are the `github_repo` resources attached to it (`multica project resource list <project-id> --output json`; project ids from `multica project list --output json`). Match a repo by `owner/name`, case-insensitive, ignoring a trailing `.git` or `/`. A root ticket lives in the project whose repos include the repo it changes. Several projects match: keep the ticket where it is when its project is one of them, else ask its human owner. No project matches: the repo is outside the factory's scope; leave the ticket where it is, flip it `blocked` and ask its human owner. A ticket that changes no repo stays in the project it was filed in. No skill, instruction or squad briefing lists projects or repos; the attached repos are the list. (Policy 05 statement 7c.)
- Every child lives in the same project as its root. Titles: **root tickets carry one type prefix** — `[Feature]` · `[Enhance]` · `[Bug]` · `[Question]` · `[CICD]` · `[Docs]` · `[Design]` — matching the type label, set by product-owner at intake (or by the first agent to pick the ticket up where product-owner never does); create with a plain title and let it prefix. Children carry `[S<num>]` spec review, `[P<num>-n]` phase tickets (`<num>` = root key number), `[D<num>-n]` dev sub-tasks (`<num>` = phase key number, `n` = stage) — never a type prefix, and the `<num>` keying is off the root's key NUMBER, never its title. Labels on root tickets only.
- Every sub-issue is created with `--stage <n>` and an explicit `--status` (`todo` for the active stage, `backlog` for later ones), parented directly to its cycle parent. Verify with `multica issue children <parent> --output json` after creating.
- Only squad leaders run `multica issue create` (product-owner in product-team, dev-leader in dev-team). Members report on their own sub-task in filable shape.
- Set the `Owner` property on every issue you create, copied from the parent. To find the human owner of any ticket: its `Owner` property, else the nearest ancestor's, else the root creator when `creator_type` is `member`, else the workspace owner. Never hardcode a member name or UUID.
- Durable gate state goes on custom properties (`Gate verdict`, `Gate round`, `Gate score`), never on issue metadata.
- `Wake count` (number) is written by `run-medic` alone: how many times the hourly run-recovery autopilot has woken this issue after a transient run failure. At 3 it stops and hands the issue to its human owner. Never set, clear or read it as part of cycle work.
- `Retrigger on done` (text, one issue key or several comma-separated: `DRK-1703,DRK-1704`) marks a sub-task whose completion must re-trigger one or more `blocked` issues — a `done` above a blocked stage fires no barrier, so without it the leader has no record of which gate to re-arm. The leader sets it on every sub-task it re-triggers for fix work (a re-armed Build, or a Fix sub-task filed above a blocked gate): `multica issue property set <id> --name "Retrigger on done" --value <blocked-key>[,<blocked-key>…]` — a sub-task that already carries it gets the new key appended, never overwritten. Leader on every wake: each `done` child carrying it → for every key it names, once every child naming that key is `done`, flip that issue `in_progress --no-start` and post ONE comment there with its assignee's mention pointing at the fix report; then set the property to the keys still waiting, or `multica issue property unset <id> --name "Retrigger on done"` when none is left. Members never set or clear it.

## Git and PRs

- `dev` is integration, `main` is release. Feature branches come from fresh `origin/dev`; every feature PR targets `dev`. Only release-manager targets or merges `main`.
- PR titles start with the ticket key in `[KEY]` form. Never write `Closes`/`Fixes`/`Resolves` next to an issue key: close intent auto-completes the ticket and kills the remaining phases.
- The publish pipeline computes the release number from the tags — never hand-edit a version literal (`Directory.Build.props`, `package.json`) and never create a tag or GitHub Release yourself; the one exception is devops' `Chart.yaml` `version` bump on a chart change (patch, or minor for a breaking change, never major — `HELM-DEL-002`). A normal release is a patch (`v1.2.3` → `v1.2.4`) and needs no marker. A **breaking change carries `(MINOR)`** in the commit title, so the pipeline cuts `v1.3.0`. **Never write `(MAJOR)`** in any commit title, PR title or merge-commit subject: the major number is the owner's call alone, taken outside a cycle (Policy 08 statement 12).
- `gh pr create` always carries both `--head` and `--base`. Never `git checkout` a shared branch; stay on your `agent/...` branch and push by refspec.
- **Members never create, cut or push a branch.** The `agent/...` branch the runtime puts you on is a scratch worktree, never a delivery target: never push it, and never run a bare `git push` (with no refspec it pushes that name to origin). You deliver only with `git push origin HEAD:refs/heads/<feature-branch>` and prove it with `git ls-remote origin <feature-branch>`, quoted in your report — the remote SHA, never the local `origin/<branch>` tracking ref, which a bare push leaves looking correct (DRK-1353, Policy 03 §3c). If the leader named no branch, or `git ls-remote origin <branch>` comes back empty, the cycle is not ready for you: flip `blocked` and ask the leader for the branch with their mention. Creating it yourself is a defect even when the code is right.

## Reports and reads

- Comment bodies are written to a file in your working directory and posted with `--content-file`; issue bodies with `--description-file`.
- Read threads bounded: `multica issue comment list <id> --roots-only --summary --compact`, then `--thread <id> --tail 30` for the threads that matter.
- Completion and blocker comments use the shapes in `blocker-report`. Every claim cites `file:line`; no evidence, no claim.
