# mx-workspace — factory constants

The Monxa Payment Gateway Platform: .NET service repos under `github.com/the-wixo`
(`monxa.payment-gateway`, `monxa.auth-api`, `monxa.email-service`,
`monxa.web-hook-deliverer`, `monxa.bdd-integration`, `monxa.helm-charts`). Unlike a
library workspace, Monxa is deployed: `dev` is INTEGRATION, `main` is SANDBOX (argoCD),
and production tagging happens automatically in CI/CD downstream — no agent tags a
release. Governance lives in the repo's `docs/policies/`; the shared flow lives in
`sdlc-flow-delivery-pipeline`; role procedure lives in your skills. The rules below hold
for every agent on every run; where a skill or squad briefing repeats one, this is the
canonical statement.

## Status and wakes
- A child ticket ends every reporting turn at `done` (work complete) or `blocked` (needs someone). Never `in_review` on a phase ticket or sub-task: it is non-terminal, closes no stage barrier, and wakes nobody. Ignore any brief or system comment that asks for `in_review` on a child. `in_review` is only a squad leader's flag on a PARENT issue whose deliverable awaits human review — never on your own sub-task, and never on the main ticket, whose terminal states are `done` or `cancelled`.
- `done` is one-way for the assignee. A member never flips its own sub-task out of `done` — a stage barrier re-fires on every re-entry into `done`. Work that comes back arrives as a comment carrying the assignee's agent mention. The leader alone re-triggers fix work: first flip the ticket to `in_progress` (`multica issue status <id> in_progress --no-start`, so the flip itself starts no run), then post the mention, so the board shows the fix in flight; the assignee ends that turn at `done`/`blocked` as always.
- On wake, if your ticket is `todo`, flip it `in_progress` before working. Last commands of every reporting turn: read your ticket's status back and correct it if it is not `done`/`blocked`, then post your handoff line when one is due (below).
- One wake per handoff. A run is enqueued by: assignment or promotion out of `backlog` into `todo`; a `done` or `cancelled` that closes a stage (the platform's sub-issue rule, below); an agent/squad mention with a real UUID; and an agent's plain comment (no mention of any kind) on a squad-assigned ticket or on any sub-task under one, which wakes that squad's leader (so a member's report on its own sub-task wakes the leader alongside the barrier or handoff line for that event; the leader's wake guard ignores the echo — Policy 05 statement 5a, `sdlc-flow-squad-leader-playbook`). Nothing else: `blocked`, a `done` that closes no stage, a re-arm flip (`blocked`/`done`→`in_progress --no-start`), a flip from `blocked`/`done` into `todo`, and a plain comment on any other ticket all enqueue nothing — a ticket that has already run is never re-woken by its status, so there the mention is the wake. When the status transition already wakes the next actor, do not also mention them. Mentions are NOT deduped — one mention, one run, even when the target is already `queued` or `running`. Post at most one mention comment per turn, last. Every `mention://agent/<uuid>` link in a comment or description is a wake for that agent, even inside backticks or quoted instructions: write instructions about mentioning someone in prose, never paste the link.
- **Stage wake and handoff line.** The platform's sub-issue rule wakes the parent's assignee (a squad's leader, in leader role) when every sub-issue at a stage and below is `done`/`cancelled` while a later stage waits, and once more when every sub-issue is closed — whoever closed them. So a plain `done` posts nothing more. The rule stays silent in two cases, and there the child's turn ends with ONE handoff line on its PARENT, after the report on the child and the status flip: the child goes `blocked` (`<KEY> blocked — BLOCKER on <KEY>`), or it goes `done` while a sibling at its stage or below sits `blocked` — check `multica issue children <parent-id>` after every `done` (`<KEY> done — report on <KEY>`). Anything else the parent's owner must read now takes the same line (`<KEY> — <what> on <KEY>`). The line is the wake; the report, the blocker and every discussion stay on the child. On a squad-assigned parent — every main and phase ticket here — it carries no mention of any kind: the platform routes an agent's plain comment there to the squad leader, and any agent, squad or member mention, `@all` or a `/note` prefix stops that. On an agent-assigned parent (an autopilot run issue) it ends with that agent's mention. On a member-assigned parent none is posted.
- A member writes only on its own ticket (comments, status, properties) plus its handoff line on the parent. It never comments on, mentions, or changes another member's ticket. Anything meant for another member (review findings, a fix request, a question) is a comment on the member's OWN ticket, and its handoff line wakes the leader, who routes it. Only the leader writes on tickets it does not own. Leader↔member traffic lives on the member's own sub-task; the handoff line is the only thing a member posts on the parent, whose other comments belong to the parent's owner.
- Humans are reached by ASSIGNMENT, never by mention: a member mention renders a link and delivers nothing. Reassign the ticket that needs them to their member UUID at `todo` (`multica issue update <id> --assignee-id <member-uuid> --status todo`) with a `## BLOCKER` comment on that ticket (`blocker-report`). Comments on the requester's own main ticket are the one exception — they watch what they filed. Never agent-mention a human, and never take a ticket back while a human holds it.
- **Never run a long command in the background.** A run cannot resume around a backgrounded process: your turn ends, the process is orphaned, and the next run starts in a fresh checkout with nothing to collect. Run tests, builds and packs synchronously with a longer timeout, and split a suite too big for one call into chunks that each finish inside their own call. Never end a turn waiting on something you launched in the background.

## Tickets
- Each squad files into its OWN home project, not the root's: `mx-main` holds main tickets, `[S<num>]` spec reviews and `[P<num>-n]` phase tickets (product-team); `mx-code` holds `[D<num>-n]` dev sub-tasks (dev-team); `mx-qc-board` holds `[T<num>-n]` QC sub-tasks (qc-team); `mx-jobs` holds autopilot run issues; `mx-prd-releases` holds prd-release's SANDBOX→PRD promotions. `<num>` is the ROOT main ticket's key number, `n` the stage. Main tickets carry one ROOT type prefix — `[Feature]` · `[Enhance]` · `[Bug]` · `[Question]` · `[CICD]` — matching the type label, set by product-owner at intake (or by the first agent to pick the ticket up where product-owner never does); create with a plain title and let it prefix. A type prefix on a sub-task, or another squad's child prefix in your home project, is a defect, not a style slip. `<num>` keying is off the root's key number, never its title. Labels on main tickets only. Resolve project IDs at runtime.
- Every sub-issue is created with `--stage <n>` and an explicit `--status` (`todo` for the active stage, `backlog` for later ones), parented directly to its cycle parent. The stage number in the title is decoration; the `--stage` field is the mechanism — an unstaged child sits in no barrier group, so its `done` fires nothing, with no error and a board that still looks healthy (MXW-1187 died exactly this way). Verify with `multica issue children <parent> --output json` after creating: every child of yours must sit inside a `stages` group, never in `unstaged`.
- Only squad leaders run `multica issue create` (product-owner in product-team, dev-leader in dev-team, qc-leader in qc-team). Members report on their own sub-task in filable shape and let the leader file.
- Set the `Owner` property on every issue you create, copied from the parent; an agent filing a root ticket sets it to the human the work is for. To resolve the human owner of any ticket, in order: its own `Owner` property, else the nearest ancestor's walking `parent_issue_id` toward the root, else the ROOT main ticket's `creator_id` when `creator_type` is `member`, else the workspace owner. Never hardcode a member name or UUID.
- `Retrigger on done` (text, one issue key or several comma-separated: `MXW-1703,MXW-1704`) marks a sub-task whose completion must re-trigger one or more `blocked` issues. The leader sets it on every sub-task it re-triggers for fix work (a re-armed Build, or a Fix sub-task filed at the RAISING stage above a blocked gate) — `multica issue property set <id> --name "Retrigger on done" --value <blocked-key>[,<blocked-key>…]` (a sub-task that already carries it gets the new key appended, never overwritten) — because a `done` above a blocked stage fires no barrier and the leader would otherwise have no record of which gates to re-arm. Leader on every wake: each `done` child carrying it → for every key it names, once every child naming that key is `done`, flip that issue `in_progress --no-start` and post ONE comment there with its assignee's mention pointing at the fix report; then set the property to the keys still waiting, or `multica issue property unset <id> --name "Retrigger on done"` when none is left. Members never set or clear it.
- A Fix sub-task is filed at the stage that RAISED the failure, never a new or higher one — a fix above the blocked stage is a phantom barrier that orphans it.

## Git and PRs
- `dev` is INTEGRATION, `main` is SANDBOX. Feature branches come from fresh `origin/dev`; every feature PR targets `dev`, one PR per squad cycle. Only the squad leaders (`dev-leader`, `qc-leader`) cut branches and open PRs, inline per `leader-gitops` — never as Branch or PR sub-tasks. Only `release-manager` opens or merges the `dev`→`main` release.
- PR titles start with the ROOT main ticket's key in `[MXW-XXX]` form so Multica autolinks it. Never write `Closes`/`Fixes`/`Resolves` next to an issue key in a title or body: close intent auto-completes the ticket and kills the remaining phases. Check for an existing open PR before opening a second.
- `gh pr create` always carries both `--head` and `--base`. Never `git checkout` a shared branch; stay on your `agent/...` branch and push by refspec.
- **Members never create, cut or push a branch.** The `agent/...` branch the runtime puts you on is a scratch worktree, never a delivery target: never push it, and never run a bare `git push` (with no refspec it pushes that name to origin). You deliver only with `git push origin HEAD:refs/heads/<feature-branch>` and prove it with `git ls-remote origin <feature-branch>`, quoted in your report. If the leader named no branch, or `git ls-remote origin <branch>` comes back empty, the cycle is not ready for you: flip `blocked`, ask for the branch on your own ticket, and post your handoff line. Creating it yourself is a defect even when the code is right (DRK-1353: a bare push left the fix on `agent/dev-backend/1b37847e15ca` while the feature branch still sat at `at_sha`, and the leader had to fast-forward it by hand).

## Reports and reads
- Comment bodies are written to a file in your working directory and posted with `--content-file`; issue bodies with `--description-file`. Clean the file up after posting.
- Read threads bounded: `multica issue comment list <id> --roots-only --summary --compact`, then `--thread <id> --tail 30` for the threads that matter.
- Completion and blocker comments use the shapes in `blocker-report`. Every claim cites `file:line`; no evidence, no claim. A partial run is reported as partial, never as clean.
- Never trust a hardcoded UUID from documentation. Resolve at runtime: `multica agent list` / `squad list` / `project list` / `workspace member list`, all `--output json`.
