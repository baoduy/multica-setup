# Multica release review — v0.7.1..v0.7.2 (2026-11-02)

Installed: multica 0.7.2 (CLI and daemon on Stevens-Mac-mini, commit f05a525ac,
server URL `http://localhost:8080`). The server version cannot be read from the CLI.
Every server-side change below applies only once the server is on that release or later.
Releases: v0.7.1 (2026-10-27), v0.7.2 (2026-10-30). 109 changelog lines. 37 PRs read in
full; the rest are listed under Skipped. Run by setup-steward on DRK-2497 (weekly retro
DRK-2495).

## Summary

1. **Code mentions no longer wake anyone (#7397, v0.7.1).** A `mention://agent/<uuid>`
   link inside inline code, a code span or a fenced block is now inert. A link in prose
   or in a blockquote still wakes. Two texts state the opposite:
   `workspace/workspace.context.md:10` ("even inside backticks") and Policy 10 statement 6
   ("a wake wherever it appears"). Their rule, "state the recipe, never paste the link",
   stays safe, because it is stricter than it needs to be. The real risk runs the other
   way: a template that puts a real wake mention inside a fence now wakes nobody. Owner
   decision (P1).
2. **Agents can steer running turns (#9630, v0.7.2).** The platform now adds a hard rule
   to every squad leader briefing when the daemon advertises `cli-comment-steer-v1`.
   Daemon 0.7.2 does. The rule says: correct a running worker with `issue comment add
   --steer <run-id>`. The CLI adds a mention by itself. A steer the turn never reads is
   replayed as a follow-up run, so a steer is a wake source the drunk wake contract does
   not list. Owner decision (P2).
3. **Autopilot runs no longer fail when their issue goes `blocked` (#9472, v0.7.1).**
   On failure, Drunk Live Sync, Monthly Insights and the Weekly Setup Retro set their
   issue `blocked`. Those runs now show `completed` and stop counting toward the
   failure-rate auto-pause. Watch issue status, not the run list (Breaking, below).
4. **`multica issue rerun-task <run-id> [--fresh]` (#9592, v0.7.2).** It reruns a
   specific run with its original agent and trigger context. Run-recovery could use it
   instead of a mention reply. That adds a wake source and changes the run-medic charter.
   Owner decision (P3).
5. **`--until-issue-state blocked` (#9553, v0.7.1).** A leader can now wait on a child's
   `done` and on its `blocked`. Together these can replace the handoff line and
   `Retrigger on done`. Still blocked on wakeups being off (P4; carries the 2026-10-26
   P2/P3).
6. **Claude session/weekly limits (#9652, v0.7.2).** These runs are now classified as
   quota failures. They no longer hang while a Claude background task lives. Run-recovery
   treats them as PERMANENT already, by default. No change.

Implemented in this run: nothing. Each proposal amends a policy statement or the wake
contract, or needs a server endpoint whose version cannot be confirmed.

## Proposals

### P1 Code-span mentions are inert: reword the "wake wherever it appears" rule — breaks assumption (owner)
- Feature: `ParseMentions` uses CommonMark link nodes and skips code. Inline code,
  multi-line code spans, indented code, and backtick or tilde fences (also inside lists,
  blockquotes and `<details>`) are inert. A mention in a blockquote in prose still wakes.
  Noncanonical, titled, reference-style and invisible-label links are inert too. From
  #7397 in v0.7.1. The platform `mentions.md` reference says the same. Needs upgrade:
  server ≥ v0.7.1, not confirmed.
- Setup today: `workspace/workspace.context.md:10` says "Every `mention://agent/<uuid>`
  link in a comment or description is a wake for that agent, even inside backticks or
  quoted instructions". `docs/policies/10-ticket-ownership-and-owner-pickup.md:88`
  (statement 6) says "it is a wake wherever it appears, so an instruction states the
  recipe and never the link". The drunk mention form `[@<name>](mention://agent/<id>)` is
  canonical, with a visible label, so every deliberate wake still works.
- Hazard to watch: run-recovery shows its wake body in a fence
  (`autopilots/hourly-run-recovery.description.md:89-97`, mention on the first line). If
  run-medic posted that fence literally, the mention would now wake nobody. No live sample
  exists to check. The last run-recovery runs with a candidate (DRK-2453, DRK-2454,
  2026-10-25/26) were permanent failures with no wake. Agent comments on DRK-2397..DRK-2497
  carry no agent mention link at all, in code or out of it. On the next class-A or
  class-B wake, check that the mention renders as a link.
- Change: none until the server is confirmed on v0.7.1+. Then reword both sentences. A
  link in prose or in a blockquote wakes; a link inside code does not. Never rely on
  code to make a link inert, and still write the recipe, not the link.
- Policy impact: Policy 10 statement 6, plus the workspace context sentence that quotes
  it. **Needs owner approval.**
- Benefit / risk / effort: accurate wake rules / none if the "recipe, not link" rule
  stays / S.

### P2 Decide how drunk leaders use steering — new capability, breaks assumption (owner)
- Feature: `multica issue comment add <issue> --content-file f --steer <run-id>`
  (repeatable) or `--steer-active` adds the comment to a running turn. The steerer must
  be allowed to start that agent. It cannot steer its own run. The cap is 3 messages per
  author per run and 10 from all agents. Attachments are not allowed. The CLI mentions
  each steered agent. If the turn ends before it reads the steer, the comment is
  replayed as a follow-up run. The squad leader briefing gains `squadSteerRule` ("To
  correct it mid-run … steer that run instead") when the daemon advertises
  `cli-comment-steer-v1`. From #9630 in v0.7.2. Needs upgrade: server ≥ v0.7.2, not
  confirmed. CLI and daemon 0.7.2 already have `--steer`.
- Setup today: the wake contract lists every enqueue source and ends with "Nothing else"
  (`workspace/workspace.context.md:10`). That paragraph also says "Post at most one
  mention comment per turn, last". Leader↔member traffic lives on the member's own
  sub-task (`workspace/workspace.context.md:13`). Mentions are actions (Policy 05
  statement 6, `docs/policies/05-sdlc-delivery-lifecycle.md:103`). The platform rule
  targets workers running on "this issue". drunk members run on their own `[D…]`
  sub-tasks, not on the parent, so on the parent the rule mostly finds no run. It
  applies when a leader comments on a member's sub-task while that member is running.
- Change (if adopted): add one line to the leader playbook. A correction to a member
  mid-Build goes on that member's sub-task with `--steer <run-id>`, and counts as the
  turn's one mention comment. Add "a steered comment (replayed as a follow-up run when
  unread)" to the enqueue list. If not adopted: add a line telling leaders not to steer,
  because the platform briefing invites it.
- Policy impact: Policy 05 statements 5 and 6, and the workspace context wake list.
  **Needs owner approval.**
- Benefit / risk / effort: a leader can stop a Build going the wrong way before it
  finishes / one more wake path, and the auto-added mention can break "one mention,
  last" / S.

### P3 Run-recovery reruns the failed run instead of mentioning — replace workaround (owner)
- Feature: `multica issue rerun-task <run-id> [--issue <id>] [--fresh]` repeats a
  specific run with its original agent, even after reassignment. It keeps the trigger
  context and `rerun_of_task_id` lineage, and reuses the session and workdir unless
  `--fresh`. `issue rerun <issue>` is deprecated and hidden. The bundle uses neither.
  From #9592 in v0.7.2. Needs upgrade: the server needs the new
  `POST /api/tasks/{id}/rerun` endpoint (≥ v0.7.2), not confirmed.
- Setup today: run-recovery wakes a class-A issue with a reply that opens with the
  crashed agent's mention and a generic "Retrying now" text
  (`autopilots/hourly-run-recovery.description.md:87-97`). The run-medic charter
  describes waking by comment (`docs/policies/09-agent-roles-and-responsibilities.md:202-205`).
- Change: for class A only, run `rerun-task <failed-run-id>`. Keep a reply without a
  mention as the audit record, and keep the `Wake count` cap unchanged. Class B
  (completed run, ticket left open) keeps the mention, because rerunning a completed
  run's trigger would repeat finished work.
- Policy impact: the workspace context wake list (`:10`, "Nothing else") and the
  Policy 09 run-medic charter. **Needs owner approval.**
- Benefit / risk / effort: the agent resumes its real instruction, not a generic nudge /
  new code path in an hourly autopilot / M.

### P4 `--until-issue-state blocked` completes the wakeup set — replace workaround (owner; carries 2026-10-26 P2/P3)
- Feature: `multica issue wakeup create <parent> --until-issue <child>
  --until-issue-state blocked` fires once when the child reaches `blocked`. The run's
  condition facts carry the child id and status. From #9553 in v0.7.1. Needs upgrade:
  server ≥ v0.7.1, not confirmed.
- Setup today: a child that goes `blocked`, or `done` beside a blocked sibling, posts
  one handoff line on its parent, because the stage rule is silent there
  (`workspace/workspace.context.md:11`). A fix above a blocked gate is re-armed through
  `Retrigger on done` (`:26`).
- Change: none until the owner turns wakeups back on. The 2026-10-26 P3 re-test of
  wakeup dispatch comes first. With `done` and `blocked` both watchable, a leader-side
  wakeup per child could replace the handoff line and `Retrigger on done`.
- Policy impact: Policy 05 statement 5 and the workspace context Status and wakes
  section. **Needs owner approval.**
- Benefit / risk / effort: removes the most error-prone manual wake / depends on
  dispatch health / L.

## Breaking or behaviour changes to verify

- **Autopilot runs and `blocked` issues (#9472, v0.7.1).** A `create_issue` run now
  completes when its first linked task completes. It no longer fails when the issue goes
  `blocked`. It fails only if the task fails terminally, or the issue is cancelled
  before any task finishes. On failure, Drunk Live Sync
  (`autopilots/drunk-live-sync.description.md:33`), Monthly Insights
  (`autopilots/monthly-claude-code-insights.description.md:93`) and the Weekly Setup
  Retro (`autopilots/weekly-setup-retro.description.md:92`) set their issue `blocked`.
  Those runs now show `completed` and no longer feed the failure-rate auto-pause.
  Nothing in the bundle reads autopilot run status (a grep for auto-pause and
  failure-rate finds nothing). A failed sync now shows only as a `blocked` issue. History
  is not backfilled.
- **Project workflows are GA (#9535, v0.7.1).** Every member can now create workflows and
  attach them to projects. With a workflow attached, the runtime brief drops its
  built-in `in_progress`/`in_review` rules (#9415), the squad leader protocol switches to
  workflow terms, and a handler-less step is briefed as one span (#9546). Each would
  contradict the Status and wakes rules (`workspace/workspace.context.md:7-13`). All six
  drunk projects still have `workflow_id: null` (checked 2026-11-02). Without a workflow
  the brief is byte-identical (#9415), and PR-merge auto-status is unchanged on Default
  (#9598). Keep every drunk project on Default unless the owner amends Policy 05.
- **Mention refusals are recorded (#9624, v0.7.2).** A mention the author may not invoke
  now gets a system reply under the comment. That includes a wrong or made-up UUID,
  which looks the same as a denied one on purpose. `workspace/workspace.context.md:10`
  says "a plain name or a wrong id silently wakes nobody". A wrong id is no longer
  silent but still wakes nobody. A plain name is still silent. These are replies, not
  roots, so run-recovery step 7 ("NEWEST root comment that you did not author", `:87`) is
  unaffected. The retro can cite such a reply as evidence of a bad mention.
- **Claude limits (#9652, v0.7.2).** `You've hit your session limit` and `… weekly limit`
  now classify as `agent_error.provider_quota_limit`. The daemon also kills Claude 10 s
  after an error result instead of keeping the run open while a background task lives.
  Run-recovery step 5 (`autopilots/hourly-run-recovery.description.md:80-83`) matches
  neither phrase, so the run defaults to PERMANENT and is not woken. That is correct: a
  retry before the reset fails again. Runs that used to hang now end as failed instead
  of looking abandoned (class B).
- **Edited trigger comments (#9526, v0.7.1).** A run that resumes after its trigger
  comment was edited now gets `[EDITED COMMENT]` and a note that only the edited text
  counts. No change.
- **Shorter Available Commands (#9596, v0.7.2).** Detail moved behind `--help` and the
  platform references. The workspace context restates none of it. No change.
- **Removed daemon capabilities (#9671, v0.7.2).** `execution-manifest-v1`,
  `agent-skill-v1` and `remote-mcp-v1` are gone. The bundle names none of them. Only
  servers v0.4.25–v0.4.29 with `plugins_v1` on are affected.
- **Skill file paths (#7743, v0.7.1).** Skill create, update and `files upsert` now
  reject absolute, backslash, traversal, NUL and non-canonical paths. Every path under
  `export/drunk-workspace/skills/` is canonical (checked with `find`), so the live sync
  is unaffected.
- **Skill refresh is all-or-nothing (#9518, v0.7.1).** A source refresh fails instead of
  publishing a partial bundle. This matters only if someone refreshes archify from its
  import origin. The bundle sync does not use refresh.
- **Reserved custom args (#9560, v0.7.1).** Saving an agent with blocked `custom_args`
  now returns 400. Every `agents/*.json` has `custom_args: []`.
- **Stalled HTTP/2 connections (#9551, v0.7.2).** The daemon pings an idle HTTP/2
  connection and reconnects after host suspend. Expect fewer timeout failures after the
  Mac mini sleeps. No change.
