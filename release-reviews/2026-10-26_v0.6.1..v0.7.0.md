## Summary

1. **Duplicate cancels can now carry the link (#8979, v0.6.1).** `issue status <id>
   cancelled --duplicate-of <original>` records the duplicate mark, so the original
   lists it. Five bundle sites cancelled duplicates with a plain `--status cancelled`.
   Implemented (P1).
2. **`--until-pr` only watches PRs linked to that exact issue (#9066 doc, v0.6.2).**
   drunk PR titles carry the ROOT key, so the 2026-09-28 P6 (a CI wakeup on the Review
   sub-task) would sit at `Condition pending` forever as written. P6 has to target the
   root. Owner decision (P2).
3. **Wakeup dispatch was rebuilt (#9202, v0.6.2).** Two lanes, 15 s / 1,500-rule passes.
   The owner turned wakeups off on 2026-09-29 because dispatch timed out against the
   remote Postgres, and the stage-barrier rule is a wakeup rule too. This is the
   release to re-test that on (P3).
4. **A leader woken by a wakeup keeps its leader role from v0.7.0 (#9427).** Before,
   that run lost `is_leader_task`, so the 2026-09-28 P7 could not have worked on any
   earlier version. Now viable, still owner-only (P2).
5. **`multi_text` property type (#8559, v0.6.2)** fits `Retrigger on done`, which is
   a comma-separated `text` today. The type is immutable, so it needs a live migration
   (P4).
6. **Security fixes with upgrade pre-checks (#9423, #9469 in v0.7.0).** Daemon routes
   now enforce runtime ownership (migration 588). Run the two SQL checks before the
   server upgrade if it has not happened yet (Breaking, below).

## Proposals

### P1 Cancel duplicates with `--duplicate-of` — new capability (implemented)
- Feature: `multica issue status <id> cancelled --duplicate-of <key>` (and `issue
  update <id> --duplicate-of <key>`, which implies cancelled) records the duplicate
  mark and lists the duplicate on the original. A non-`cancelled` status with the flag
  is rejected; the server refuses self-reference and an original that is itself a
  duplicate. From #8979 in v0.6.1 (server support since v0.5.2). The runtime brief now
  says a plain cancel plus a comment leaves no link. Needs upgrade: no.
- Setup today: duplicates were cancelled with `multica issue update <id> --status
  cancelled` at `skills/sdlc-flow-squad-leader-playbook/references/recovery.md:22`
  (duplicate chains or sub-tasks), `:29` (duplicate root before decomposition), `:37`
  (duplicate root after a failed merge),
  `skills/sdlc-flow-po-orchestration/references/workflow-c-edge-cases.md:7` (duplicate
  phase tickets) and `skills/sdlc-flow-squad-leader-playbook/references/issue-filing.md:17`
  (a member-filed issue folded into the leader's).
- Change: those five commands become `multica issue status <id> cancelled
  --duplicate-of <kept key>`. The cancel of a duplicate root's own sub-tasks
  (`recovery.md:35`) stays a plain cancel: they are not duplicates. The live-run
  `cancel-task` step before each cancel stays.
- Policy impact: none. Policy 07 statement 8a ("dev-leader cancels the newer root with
  one comment that links the older one") is unchanged; only the command changes, as
  with the 2026-09-28 P3.
- Benefit / risk / effort: the older root lists every duplicate, so the retro and the
  owner can count duplicates without reading comments / `cancelled` closes a stage
  exactly as before / S.

### P2 Revisit the 2026-09-28 P6 and P7 (wakeup conditions) — replace workaround (owner)

- Setup today: pr-reviewer polls CI in the foreground for up to 30 minutes
  (`skills/pr-review-gate/SKILL.md:122`). The PR title carries the ROOT key
  (`docs/policies/03-source-control-branching.md:61`, `skills/leader-gitops/SKILL.md:28`),
  so the PR is linked to the root, never to the Review sub-task. A fix above a blocked

  statement 5 would change. **Needs owner approval.** The 2026-10-07 audit records that
  the owner turned wakeups off on 2026-09-29; see P3 first.
- Benefit / risk / effort: shorter pr-reviewer turns, a conflict wake without polling /
  new code path in a gate skill, one more wake source / M.

### P3 Re-test wakeup dispatch on this server — breaks assumption (owner, live)
- Feature: the dispatcher drains input receipts and due checks in two interleaved
  lanes, capped at 15 s or 1,500 rules per pass, with new log fields (`input_rules`,
  `due_rules`, `stopped`, `oldest_ready_input_age_s`) (#9202, v0.6.2). Expect longer
  passes (~14 s for ~1,200 rules).
- Setup today: the 2026-10-07 audit (`docs/drunk-setup-audit-2026-10-07.md:184-187`
  at the repo root) says wakeups were turned off on 2026-09-29 against a 2-second
  dispatch budget on the remote Postgres, and CHANGELOG 2026-09-29 (b) says the
  platform stage rule "still times out against the Azure database". The bundle now
  relies on that stage rule (`workspace/workspace.context.md:11`).
- Change: none in the bundle. Owner: read the server's dispatch logs for
  `stopped=drained` and pass length, and spot-check `multica issue wakeup list
  <parent>` on an active cycle for a non-null `last_error` (stale errors now clear,
  #9069, so a clean value means healthy now, not never failed).
- Policy impact: none.
- Benefit / risk / effort: decides whether P2 is possible at all / none / S.

### P4 `Retrigger on done` as a `multi_text` property — replace workaround (owner, live)
- Feature: `multi_text` / `multi_url` property types (#8559, v0.6.2, migration 564).
  `issue property set --value "a,b"` (or a JSON array) REPLACES the whole list, max 20
  entries, duplicates dropped; `issue list --property "Name=<entry>"` matches one entry
  exactly. Since v0.7.0 a text property also supports `Name~=value` (contains, #8001).
  Needs upgrade: no.
- Setup today: `Retrigger on done` is `text` holding comma-separated keys
  (`workspace/workspace.context.md:26`, `properties/properties.json:92`); the leader
  appends by rewriting the string.
- Change: create a new `multi_text` property (types are immutable), copy the open
  values across, retire the old one, then reword the workspace context. The
  read-then-rewrite append stays (the CLI replaces, it does not append).
- Policy impact: the workspace context statement on `Retrigger on done`. A live
  property migration, outside setup-steward's reach. **Owner decision.**
- Benefit / risk / effort: one key per entry, exact filtering / migration of in-flight
  values / M. Low value while the append rule is unchanged.

## Breaking or behaviour changes to verify

- **Server upgrade to v0.7.0 (#9423, migration 588).** Daemon routes now require the
  caller to own the runtime; a daemon re-registering under a different member gets 403.
  Before upgrading, run:
  `SELECT count(*) FROM agent_runtime WHERE owner_id IS NULL AND daemon_id NOT LIKE 'qoder-managed-%';`
  and `SELECT workspace_id, daemon_id FROM agent_runtime WHERE daemon_id IS NOT NULL
  GROUP BY 1,2 HAVING count(DISTINCT owner_id) > 1;`. Any row needs an owner first.
  Tasks running across the upgrade may see Remote MCP `credential revoked` errors until
  their token expires (#9469 narrows this).
- **CLI and daemon on the same version per host (#9217, v0.6.2).** A daemon that cannot
  bind its profile port records a fallback in `daemon.port`. An older CLI ignores that
  file, reports `stopped`, and may start a second daemon. The runtime brief's "compare
  the PID with `multica daemon status --output json` before killing" rule depends on
  that answer. Upgrade both together on every host.
- **Project workflows (#8814, #9293, #9388, v0.6.3 to v0.7.0).** All six drunk projects
  have `workflow_id: null`, so they follow the permissive Default workflow and no
  workflow brief is injected. If anyone attaches a named workflow, every turn on that
  project gets a `[Project workflow]` block that replaces the agent's status rules,
  can forbid `in_review` or `blocked`, and a column handoff reassigns and starts a run.
  That would contradict the Status and wakes rules (`workspace/workspace.context.md:7-13`)
  and add a wake source. Since #9388 any member can create a workflow. Keep drunk
  projects on Default unless the owner amends Policy 05.
- **Run-recovery and system failure comments (#9018, v0.7.0).** A terminal failure now
  posts a `system`-authored root comment on the task's issue, the sweeper's failures
  included. `hourly-run-recovery` step 7 replies under "the NEWEST root comment that you
  did not author" (`autopilots/hourly-run-recovery.description.md:87`); a system root
  would qualify, and later human replies there would wake no agent. Seen so far only on
  parents (DRK-2451: "Delegated task … ended in a final failure"), which run-recovery
  never wakes. Watch the next class-A wake; if it lands under a system root, exclude
  `author_type == "system"` roots in step 7.
- **Run-recovery classifies on `error` text (step 5, `:81-83`).** Tasks now carry a
  structured `failure_reason` (`runtime_offline`, `runtime_reconnect_timeout`,
  `cancelled`, `agent_error.provider_quota_limit`, `agent_error.unknown`, …), and
  upstream fixed its own substring bugs (#8967 403 usage limit as quota, #9150 status
  codes inside hex ids, #9465 `local_directory_error`). drunk's list still matches
  substrings: `500` inside a UUID would read as TRANSIENT, and `runtime did not
  reconnect within the configured grace period` (seen on dev-backend) matches nothing
  and defaults to PERMANENT. No misfire is on record; the retro should file a fix if
  one shows up. Not changed here.
- **Codex runtime CLI path (#8944, v0.6.2).** The daemon now finds the Codex CLI at
  `ChatGPT.app/Contents/Resources/codex-cli/bin/codex`. The `~/.local/bin/codex`
  symlink the owner added on 2026-10-05 is no longer needed on daemon ≥ 0.6.2 (owner
  memory, not the bundle).
- **Codex resume and rate limits (#9020, #9218, #8934).** Long Codex threads resume
  without overflowing (`excludeTurns`), and two Guardian 429s interrupt the turn with a
  `429` error, which run-recovery classifies TRANSIENT and wakes after the hour. Fine.
- **Telemetry (#9435, v0.7.0, migrations 589–591)** adds bucketed member counts to the
  daily anonymous snapshot. `DO_NOT_TRACK` is still the opt-out; owner's call, as in
  the 2026-09-28 report.
- **Runtime visibility (#7580, #8981, #9455).** Making a shared runtime private now
  cancels teammates' running tasks, unbinds their agents and pauses their autopilots;
  binding another member's agent to your private runtime fails at save with 403. drunk
  agents are bound to two workspace-visible Mac mini runtimes; do not flip them private.
- **Effort override (#9392, v0.6.5).** Fixed silent loss of a saved Claude effort for
  models the CLI did not list. No drunk agent sets one (`runtime_config` is `{}` in
  every `agents/*.json`).
- **Autopilot schedules (#9191, v0.6.2).** Only crons firing about every minute could go
  permanently silent. drunk's densest is hourly (`5 * * * *`). Not affected.
