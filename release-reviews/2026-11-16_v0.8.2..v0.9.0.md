## Summary

1. **Hygiene Rule B still fails, and #10515 removes its stated reason (v0.9.0).**
   `multica issue delete <id>... --yes` now exists, so "Deletion has no CLI command" is false
   in the autopilot and in issue-janitor. The permission model is unchanged. An agent can
   delete only the issues it created, so the CLI would get the same 403. The two runs after
   the server upgrade say so: DRK-2540 (2026-11-15) and DRK-2542 (2026-11-16) both stopped at
   DRK-2473 with HTTP 403, and nothing was deleted. This stays the 2026-11-09 P1, an owner
   decision that amends Policy 09. Updated below (P1).
2. **The `Closes`/`Fixes`/`Resolves` rule guards against the wrong thing (#10057, v0.8.2).**
   A closing keyword only links a PR to an issue. A `[KEY]` title or a key in the branch name
   links it too. When a workspace turns PR auto-complete on, a merge completes every linked
   issue, keyword or not. drunk's workspace setting is off today (`Workspace: off`,
   `Target: none`, checked on DRK-2529), so nothing auto-completes. If that setting is ever
   turned on, the first `dev` merge will complete the root. That merge is the phase-1 PR,
   titled `[<ROOT-KEY>]`, and phase 2 is then lost. Policy 03 statement 7 gives the wrong
   cause. Owner decision (P2).
3. **A mention with a wrong id now gets a system reply (#10450, v0.9.0).** It used to vanish
   silently. A malformed id, an archived agent or a missing squad now leaves a system comment
   under the mention: "Target not found or permission not granted". Two bundle files still
   say "silently". **Implemented (P3).**
4. **The self-hosted daemon now removes old issue workdirs (#10458, #10528, v0.9.0).** The
   completed-task TTL default moved from `0` (never) to `14d` on self-hosted daemons. The
   daemon removes a workdir 14 days after its last run, even when the issue is still open.
   That includes uncommitted or unpushed work. drunk is safe: every delivery is pushed by
   refspec and proved with `git ls-remote` before the report. Verify below.
5. **Private projects are on for every workspace (#9868, #10273, v0.8.2), with hardening in
   v0.9.0.** A run on a private project is refused (`project_access_blocked`) unless both the
   triggering human and the agent's owner can see the project. All six drunk projects are
   `visibility: workspace`, so nothing changes today.

Implemented in this run: P3. P1 and P2 amend policy and are left for the owner.

## Proposals

### P1 Issue deletion is creator-only: decide what Rule B becomes — breaks assumption (owner, carried from 2026-11-09, updated)
- Feature: `multica issue delete <id>...` (#10515, v0.9.0) is the first CLI command for
  deletion. One id calls `DELETE /api/issues/{id}`. Several ids call
  `POST /api/issues/batch-delete`. The CLI reads every id first, and one bad id aborts the
  whole batch. `--yes`/`-y` skips the confirmation. A non-interactive run without `--yes`
  fails and deletes nothing. `--output json` returns `{"id":…,"deleted":true}`, or
  `{"ids":[…],"deleted":false,"deleted_count":N}` with a non-zero exit on a partial batch.
  The permissions are those of #9789 (v0.8.1): an agent task token deletes only the issues
  that agent created (`server/internal/handler/issue_delete_permissions_test.go`, case
  "agent denied sibling issue"). Needs upgrade: no.
- Setup today: Rule B deletes with `curl -X DELETE … $MULTICA_TOKEN`
  (`autopilots/weekly-issues-hygiene-cleanup.description.md:25-30`). It justifies the REST
  call with "Deletion has no CLI command" (`:17`; `agents/issue-janitor.md:15-21`). Each run
  after the server upgrade still stops at the first DELETE: DRK-2540 (2026-11-15) "Rule B
  deletion stopped at DRK-2473 … HTTP 403. Deleted: 0", and DRK-2542 (2026-11-16) the same.
  Nothing has been deleted since #9789. No owner reply on DRK-2538 or on PR #33.
- Change, owner's choice (unchanged): (a) **list, don't delete.** Rule B becomes a
  "deletion candidates" section in the report, deepest-first. The owner deletes them with
  `multica issue delete <id>... --yes` under their own login, or in the UI. (b) **Retire
  Rule B.** Either way, the REST exception and the bearer-token handling are removed. There
  is now a CLI command, so the "no CLI" reason no longer holds whatever the owner decides.
  The same edit reaches `autopilots/weekly-issues-hygiene-cleanup.description.md`,
  `agents/issue-janitor.md`, `agents/issue-janitor.description.md` and the Policy 09 charter.
  Switching Rule B to the CLI alone fixes nothing, because the 403 is a permission refusal,
  not a transport failure.
- Policy impact: Policy 09 statement 1
  (`docs/policies/09-agent-roles-and-responsibilities.md:68`, "only `issue-janitor` deletes
  issues"), the authority-matrix row (`:123`, "status + deletion only"), and the issue-janitor
  charter (`:208-210`, "via the authorized DELETE exception"). **Needs owner approval.**
- Benefit / risk / effort: the weekly report stops saying "Partial sweep" / (a) needs the
  owner to act, or (b) lets cancelled issues pile up / S.

### P2 PR auto-complete, not the closing keyword, decides whether a merge completes a ticket — breaks assumption, latent (owner)
- Feature: `multica issue create|update … --pr-auto-complete on|off` (#10057, v0.8.2) sets
  a per-issue override. `multica issue pull-requests <id>` now prints `PR auto-complete: on/off
  | Workspace: on/off | Target: <status> | State: <state>`. Its JSON gains
  `auto_complete.{state, issue_disabled, workspace_enabled, target_status, pull_request_ids}`.
  The mechanism is unchanged since v0.8.1 (`server/internal/handler/pr_auto_complete.go`):
  "A PR whose title or branch name carries an issue identifier is linked to that issue, and
  so is one whose title or body puts it after a closing keyword … The keyword only links; it
  has no say in what the merge does." When every PR linked to an issue is merged, the issue
  moves to the workspace's `pr_merge_status` (default `done`). That happens unless the
  workspace turned it off, or the issue has `--pr-auto-complete off`. Only a PR event
  triggers it. An agent task token can set the override, because the route is not
  human-only. Needs upgrade: no.
- Setup today: Policy 03 statement 7 says the keyword is what "auto-completes the ticket
  and kills the remaining pipeline phases" (`docs/policies/03-source-control-branching.md:61`,
  summary `:91`). The same rule is quoted at `workspace/workspace.context.md:31`,
  `skills/sdlc-gitflow/SKILL.md:170`, `agents/release-manager.md:25`,
  `agents/service-architect.md:35` and `agents/docs-writer.md:44`. Three promotion checks
  look for "no close intent" on the merged `dev` PR (`squads/product-team.md:41`,
  `skills/sdlc-flow-po-orchestration/SKILL.md:87`,
  `skills/sdlc-flow-delivery-pipeline/SKILL.md:69`). Live state on DRK-2529: workspace
  `off`, target `none`, state `terminal`. PR #108 is linked by branch
  (`link_source: branch`, `feature/drk-2529-…`), and its title carries `[DRK-2527]`, the
  root. So every phase-1 PR is already linked to its root and its phase ticket without
  any keyword.
- Change, owner's choice:
  - (a) **Name the real guard.** Statement 7 says the workspace keeps PR auto-complete off,
    and that turning it on would complete a root at its first `dev` merge. Keep the keyword
    ban as hygiene, with no causal claim. Replace the three "no close intent" checks with
    `auto_complete.workspace_enabled == false` from the same `pull-requests` JSON.
  - (b) **Guard each issue.** product-owner creates every root and phase ticket with
    `--pr-auto-complete off`. Then the root survives even if the workspace setting changes.
    The keyword rule can go.
  - (c) **Leave as is.** Today's setting already prevents the harm. Only the stated cause
    is wrong.
- Policy impact: Policy 03 statement 7 (`:61`) and its summary line (`:91`); (b) also
  touches the issue-creation steps in `sdlc-flow-po-orchestration`. **Needs owner approval.**
- Benefit / risk / effort: a guard that matches the mechanism; today's guard is a setting
  nobody records / none while the workspace setting stays off / S.

### P3 A wrong mention id is no longer silent — breaks assumption (implemented)
- Feature: `noteCommentInvocationDenied` now posts a receipt for `target_unavailable` too.
  Before, it posted one only for `invocation_not_allowed`. The PR's own words: it "covers
  malformed mention ids and targets that are gone (archived agent, missing squad)". Each gets
  a system reply under the comment that names the unresolved alias with "Target not found or
  permission not granted" and carries no mention link of its own. From #10450 in v0.9.0
  (`server/internal/handler/comment_invocation_notice.go`). A plain name, or a link whose id
  is not hex such as the literal `<id>` placeholder, does not match the mention pattern
  (`server/internal/util/mention.go:30`, id `[0-9a-fA-F-]+`). So it is no mention at all and
  still leaves no trace. Needs upgrade: no; the server is on v0.9.0.
- Setup today: `workspace/workspace.context.md:10` says "a plain name or a wrong id
  silently wakes nobody". `skills/pr-review-gate/references/multica-flow.md:5` says "A plain
  name, a guessed id or the literal `<that id>` placeholder silently does nothing". No
  policy restates either sentence. Policy 10 statement 6 (`:84-88`) says only to resolve ids
  at run time. The 2026-11-02 review saw the first half of this change: since #9624
  (v0.7.2), a denied mention, including a made-up UUID, gets the same reply. That review
  listed it under "verify" and did not edit. #10450 adds the malformed and gone ids, so
  every hex id that wakes nobody now gets a reply. That makes the "silently" wording wrong
  for every such id.
- Change (done): both sentences now say that none of these wakes anybody, that a plain
  name or the placeholder leaves no trace, and that a wrong id gets the system reply. A
  reader who finds that reply on a ticket can now tell it is a failed mention. There is no
  new "check and re-post" step: the reply arrives after the posting turn ends, and a second
  mention in the same turn would break "at most one mention comment per turn, last".
- Policy impact: none.
- Benefit / risk / effort: the refusal on a ticket is explained where agents read the
  mention rule / one sentence longer in every agent's context / S.

## Breaking or behaviour changes to verify

- **Workdir expiry on the self-hosted daemon (#10458, #10528, v0.9.0).** The default for
  `MULTICA_GC_COMPLETED_TASK_TTL` is now `14d` on every server. It was `0` (disabled) on
  self-host. PR #10458 says: "a self-hosted daemon will start fully removing issue-task
  environments whose last run finished more than 14 days ago, even if the issue is still
  open. That includes the checkout's uncommitted or unpushed work." Task records and
  `multica agent tasks` are untouched; only the files on disk go. #10528 also expires
  `codex-home` for local-directory runs after the same TTL. drunk is safe. Every delivery is
  pushed by refspec and proved with `git ls-remote` before the report
  (`workspace/workspace.context.md:34`, Policy 03 statement 5). Every run starts from a fresh
  checkout (`workspace/workspace.context.md:15`,
  `skills/sdlc-flow-squad-worker-playbook/SKILL.md:18`), and every drunk project resource is
  a `github_repo`. Watch a ticket `blocked` on the owner for more than 14 days. When its
  agent resumes, it will find no checkout and must clone again. The owner can set
  `MULTICA_GC_COMPLETED_TASK_TTL=0` on the daemon to keep the old behaviour.
- **Regenerable caches go after 12h (#10038 v0.8.2, #10528 v0.9.0).**
  `MULTICA_GC_ARTIFACT_TTL` (default `12h`) now also cleans `node_modules`, `.next` and
  `.turbo` on open issues, plus three Codex plugin caches. An npm cycle that resumes later
  reinstalls its dependencies. No bundle step assumes a warm cache.
- **Private projects (#9868, #10273 v0.8.2; #10317, #10320, #10327, #10329, #10282, #10312
  v0.9.0).** The `private_projects_v1` flag is gone, so the feature is on for everyone. On a
  private project, a run, an autopilot dispatch (`create_issue` or `run_only`) and a
  background run (wakeups, `child_done`, delegated recovery) are refused with
  `project_access_blocked`, unless the triggering human and the agent's owner can both see
  the project. A wakeup rule whose creator left the project is disabled.
  `multica project resource list` answers 404 to a non-member. All six drunk projects are
  `visibility: workspace` (`multica project list`, checked 2026-11-16), and the code skips
  these checks when no project is private. The workspace has one member, the owner, so even
  a private project would admit every run.
- **Comment attachments bind with the comment (#10184, v0.8.2).** Before, an upload was
  bound to the issue first, and a refused comment left it orphaned. Some uploads got a 409.
  Now upload ids are sent with the comment in one transaction. A 0.8.2+ CLI against an older
  server fails `comment add --attachment`. The server here is v0.9.0. The only bundle caller
  is `autopilots/monthly-claude-code-insights.description.md:91`
  (`--attachment <path> --allow-external-file`). `--allow-external-file` is still in
  `multica issue comment add --help`. Verify on the 2026-12-01 insights run.
- **Runtime brief wording (#10409, #10326, v0.9.0).** Instruction Precedence now says "The
  workflow never widens what your Agent Identity allows". Output now says "Post only your
  final result … one comment, or one reply per thread when the per-turn message lists
  several threads" (was "Post exactly ONE comment per run"). Available Commands gains "never
  use `git stash` / `git stash pop`" in managed checkouts. The bundle restates neither the old
  one-comment rule nor any stash step (grep for `git stash` and `one comment per run`: no
  hits). The child-report-plus-handoff-line pattern (Workspace Context, Status and wakes) is
  unaffected.
- **Sub-issue rule settings moved (#10358, #10258, v0.9.0).** The workspace on/off switch
  and default instruction for "When all sub-issues finish" moved from Settings → Wakeups to
  Autopilot → Issue wakeups. `settings?tab=wakeups` redirects there. The behaviour, the
  default and `GET/PUT /api/system-wakeups` are unchanged, and the stage wake that
  `workspace/workspace.context.md:11` relies on is the same. A turned-off rule is now folded
  into wakeup history in the sidebar.
- **Connected Apps run without per-call approval (#9849, #10177, #10268, v0.8.2).** This
  only applies with `COMPOSIO_MCP_APPS_FLAG` and a Composio key on the server. #10177:
  "Defaults do widen … Stripe write, send, and delete actions, which were previously blocked
  by default … no control to re-block them is provided." No drunk agent json grants an app.
  If the owner ever turns apps on, every granted action runs at once.
- **Issue create can answer 409 `issue_number_collision` (#10117, v0.8.2).** It used to be a
  bare 500. The server now heals a drifted counter and retries once. No bundle step parses
  the create error, so no change.
- **Squad and autopilot names resolve exact-first (#10215, v0.8.2).** `Reviewer` no longer
  collides with `Claude Reviewer`. The bundle resolves squads by id
  (`skills/sdlc-flow-po-orchestration/SKILL.md:83`).
- **Daemon and CLI fixes with no setup change:** checkout accepts another URL form of a
  registered repo (#10490), and `repo checkout` run from inside the checkout reuses it
  (#10465). darwin `EPERM` while a process group drains no longer fails a checkout (#10506),
  and the client user id is cleared on daemon-token requests (#10333). `daemon start` checks
  child health (#10207), `runtime update --wait` exits non-zero on failure (#10261), and
  self-host health is validated before saving config (#10240). The CLI no longer tells a
  live task to delete its own marker (#10224). Claude thinking text is kept in transcripts
  (#10517), and Codex text streams as it is generated (#10100). Raising an agent's
  concurrency cap wakes its runtime at once (#10463). Autopilots read map payloads on issue
  updates (#10262), and a cron that never fires stores no next run (#10239). An `@all` in a
  description no longer breaks auto-subscription (#10460), and open-only search prunes
  terminal-issue comments (#10098). mise agent shims are preserved (#10466).
- **Reverted inside the range; nothing shipped:** per-run captured file changes (#10459,
  reverted by #10548), VCS token update without webhook rotation (#10401, reverted by
  #10416), and description-image click (#10296, reverted by #10336).
