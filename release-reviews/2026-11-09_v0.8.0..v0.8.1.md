## Summary

1. **Agents can no longer delete issues they did not create (#9789, v0.8.1).** Rule B of the
   weekly hygiene sweep now fails on its first DELETE with HTTP 403. This happened on
   2026-11-08 (DRK-2534) and 2026-11-09 (DRK-2536), both times on DRK-2473, which another
   agent created. Nothing has been deleted since the upgrade. Each weekly report says
   "Partial sweep". The fix amends Policy 09. Owner decision (P1).
2. **`repo checkout` now warns on a stale cache (#9738, v0.8.0).** A failed fetch used to be
   silent. Now the CLI prints a warning, exits 0, and checks out the cached copy anyway.
   pr-review-gate checks out the PR head branch and then scores, tests and merges. It now
   confirms `HEAD` equals the PR's `headRefOid` first. **Implemented (P2).**
3. **Daemon shutdown is now a retryable failure (#9778, v0.8.0).** A run interrupted by a
   daemon shutdown used to end `cancelled`, so run-recovery never saw it. Now it fails with
   `daemon shut down while task was in flight` (reason `runtime_recovery`) and the platform
   retries it. Run-recovery's TRANSIENT list did not have that text. **Implemented (P3).**
4. **Every runtime brief now says "one issue, one PR" and "never split by layer" (#9844,
   v0.8.0).** dev-team splits a cycle by surface (dev-backend and dev-frontend, Policy 02
   statement 1g), but still opens one PR per cycle. The squad briefing carries the rule, so
   no change. The new `[Parent issue]` block gives every `[D…]` and `[P…]` run its parent's
   read commands. Verify on the next two-surface cycle.
5. **The server-version blocker on the 2026-11-02 proposals is gone.** P1 (code-span
   mentions), P2 (steering), P3 (`rerun-task`) and P4 (`--until-issue-state blocked`) were
   held because the server version was unknown. They now wait only on the owner's policy
   decisions.

Implemented in this run: P2 and P3. P1 amends Policy 09 and is left for the owner.

## Proposals

### P1 Issue deletion is creator-only: decide what Rule B becomes — breaks assumption (owner)
- Feature: issue deletion is restricted. Owners and admins can delete any issue. A member can
  delete issues they created, or that an agent they own created. An agent task token can
  delete only issues that same agent created; it does not inherit its owner's rights. A bare
  machine credential (`mcn_`) cannot delete issues. Batch delete is all-or-nothing. From
  #9789 in v0.8.1. The docs (`apps/docs/content/docs/issues.mdx`) say: "Agents can delete
  only issues they created; they do not inherit their owner's deletion rights." Needs
  upgrade: no, the server already has it.
- Setup today: Rule B deletes every issue `cancelled` for 7+ days with
  `DELETE /api/issues/<id>`, authenticated with `$MULTICA_TOKEN`
  (`autopilots/weekly-issues-hygiene-cleanup.description.md:6,15,17,25-30`;
  `agents/issue-janitor.md:11,15-21`). `$MULTICA_TOKEN` is issue-janitor's task token, and
  issue-janitor creates no issues, so every DELETE returns 403. Step 5 stops at the first
  non-2xx code (`:30`). Evidence: DRK-2534 (2026-11-08) and DRK-2536 (2026-11-09) both say
  "Rule B stopped after HTTP 403" on DRK-2473 (created by another agent). DRK-2496
  (2026-11-02, before the upgrade) was clean. Rule A is unaffected.
- Change, owner's choice:
  - (a) **List, don't delete.** Rule B becomes a "deletion candidates" section in the run
    report, deepest-first. The owner deletes the candidates in the UI. The REST exception
    and the bearer-token handling are removed.
  - (b) **Retire Rule B.** Cancelled issues stay. They are terminal and already filtered out
    of every sweep. The REST exception is removed.

  Either way the change reaches `autopilots/weekly-issues-hygiene-cleanup.description.md`,
  `agents/issue-janitor.md`, `agents/issue-janitor.description.md` and the Policy 09
  charter. Do not try to restore deletion by giving the janitor a member or owner
  credential. #9789 removed inherited owner rights on purpose, so that would be a
  credential-scope decision, not a fix.
- Policy impact: Policy 09 statement 1, `docs/policies/09-agent-roles-and-responsibilities.md:68`
  ("only `issue-janitor` deletes issues"), and the issue-janitor charter, `:208-210` (Goal
  "delete long-cancelled records children-first"; Responsibilities "via the authorized DELETE
  exception"). Also the authority-matrix row at `:123` ("status + deletion only"). **Needs
  owner approval.**
- Benefit / risk / effort: the weekly report stops saying partial / (a) the owner must act,
  or (b) cancelled issues pile up / S.

### P2 pr-review-gate confirms its checkout is the PR head — new capability (implemented)
- Feature: `multica repo checkout` reports a failed `git fetch`. The daemon returns
  `fetch_error`, and the CLI prints `Warning: fetching the remote failed, so this checkout
  comes from the cached copy and may be behind the remote...`. It still exits 0. Before this,
  the failure was silent. From #9738 in v0.8.0. Needs upgrade: no.
- Setup today: the gate checks out the head branch with `multica repo checkout <repo-url>
  --ref <head-branch>` and works from that checkout (`skills/pr-review-gate/SKILL.md:36`). It
  never compared the result with the PR head. Only the re-arm path reads `headRefOid`
  (`skills/pr-review-gate/references/multica-flow.md:65,106`). The leader cut the feature
  branch on the same host, so the cache can hold that branch at its base commit.
- Change (done): after checkout, `git rev-parse HEAD` must equal
  `gh pr view $PR -R $R --json headRefOid -q .headRefOid`. On a mismatch the gate runs
  `git fetch origin <head-branch>` and `git checkout --detach <headRefOid>` once. If the two
  still differ, it takes the existing blocked path (checkout failure,
  `references/multica-flow.md:136-138`). There is no new `Gate verdict` value, so the monthly
  insights verdict loop (`autopilots/monthly-claude-code-insights.description.md:37`) is
  unaffected. Not changed: the other `repo checkout` callers (arch-reviewer,
  release-manager, devops, docs-writer, blog-writer, medium-publishing). None of them merges
  on what it checked out, and the members and release-manager fetch `origin` themselves
  before they push.
- Policy impact: none. Policy 04 does not say how the gate checks out. No bar, cap, weight
  or severity changes.
- Benefit / risk / effort: the gate never scores, tests or merges code it did not check out /
  one extra `gh` call per review / S.

### P3 Run-recovery treats a daemon shutdown as transient — breaks assumption (implemented)
- Feature: a shutdown-interrupted run is now classified `runtime_recovery` and retried within
  the existing attempt limits. That covers a running task and a task waiting on a local
  directory lock. Its error is `daemon shut down while task was in flight`. It reaches the
  task's `error` through the fail callback (`server/internal/daemon/daemon.go:5918,6359` at
  v0.8.1). Before this, it ended `cancelled` with an empty error. A deliberate cancel still
  ends `cancelled`. From #9778 in v0.8.0. Needs upgrade: no.
- Setup today: `detect.sh` drops `cancelled` tasks
  (`autopilots/hourly-run-recovery.description.md:70`), so a shutdown-killed run was never
  recovered. Class A wakes only errors on the TRANSIENT list (`:81`;
  `agents/run-medic.md:13`), which has `daemon restarted while task was in flight` but not
  the new text. So a shutdown failure left after the platform's retries would default to
  PERMANENT. It would be reported to the owner, not woken.
- Change (done): `daemon shut down while task was in flight` is added to the TRANSIENT list
  in the autopilot, and `daemon shut down` to run-medic's short list. The `Wake count` cap is
  unchanged. The local-directory-lock variant cannot occur here, because every drunk project
  resource is a `github_repo`.
- Evidence: there is no live sample yet. Agent tasks since 2026-10-31 (first page per agent)
  hold 2 failures, both `Not logged in · Please run /login` on 2026-11-03, which is correctly
  PERMANENT.
- Policy impact: none. The run-medic charter (Policy 09 `:203`) names no error strings.
- Benefit / risk / effort: a run killed by a Mac mini restart is recovered, not escalated /
  at most 3 wakes per issue, as before / S.

## Breaking or behaviour changes to verify

- **One issue, one PR, and the `[Parent issue]` block (#9844, v0.8.0).** Every brief's
  Sub-issue Creation section now opens: split only when each piece can be merged and
  verified on its own; "slice by user-visible behavior, never by layer: a backend / frontend
  split of one feature loses the discussion behind it". dev-team splits a two-surface cycle
  into dev-backend and dev-frontend sub-tasks (`squads/dev-team.md:22`; leader playbook
  `skills/sdlc-flow-squad-leader-playbook/SKILL.md:35`, Policy 02 statement 1g), on one
  branch with one PR (`:44,72`). That matches the platform's concern: no colliding parallel
  PRs, and the parent keeps the discussion. The squad briefing holds the split, so no edit.
  The claim response now carries `parent_issue`. The daemon prints a `[Parent issue]` block
  telling a sub-issue run to read its parent and scan its threads. Workers already read the
  cycle parent, so this is now automatic. The only cycle decomposed since 2026-11-03
  (DRK-2529, Pulumi) touched one surface. Watch the next two-surface cycle for a leader
  merging the two sub-tasks.
- **Statuses follow the issue's workflow, Default included (#9540, v0.8.0).** The server now
  rejects a status the issue's workflow does not list (`400 status_not_in_workflow`), also on
  Default. The workspace stored its Default workflow on 2026-10-28. It lists all eight drunk
  statuses (`backlog`, `todo`, `onhold`, `in_progress`, `in_review`, `blocked`, `done`,
  `cancelled`), so nothing breaks today. A new custom status must be added to Default before
  agents can set it. All six projects still report `uses_default: true`
  (`multica project workflow get`, checked 2026-11-09).
- **Worktree leftovers (#9870, v0.8.1).** If an agent commits, only its commits land on the
  task branch. Uncommitted files go to `refs/multica/leftovers/<branch>/<task>`. The brief
  says so: "If you commit, only your commits are delivered". drunk agents deliver by refspec
  push and never push the `agent/...` branch (`workspace/workspace.context.md`, Git and PRs),
  so no change. A reviewer that never commits still gets its leftovers auto-committed on the
  local branch, as before.
- **CLI gaps no longer escalate to the owner (#9915, v0.8.1).** The brief now says: "If no
  command or documented platform mechanism covers what you need, report the gap in your
  result instead of working around it." The bundle never restated the old rule.
- **Codex agents cannot spawn native sub-agents (#9719, v0.8.0).** For Codex 0.145.0 and
  later, the daemon also sets `agents.enabled=false`. No Codex agent (devops, docs-writer,
  issue-janitor, Mika, run-medic) is told to spawn sub-agents.
- **Thread replies folded into a queued run (#9735, v0.8.0).** An un-mentioned reply in a
  thread whose root was folded into a queued task now continues that agent. Before, it
  started nothing. This only fixes a missed case of existing thread continuation.
- **Skill names and file writes (#7941, #9949, #9767, #9823).** The brief now gives the
  skill name actually installed after a collision, for example `review-multica`. A user skill
  named `multica-platform` can no longer pass for the built-in one. File-only skill writes
  now bump `updated_at` and publish `skill:updated`, and the live sync does not read
  `updated_at`. The import cap rose from 256 to 512 supporting files. archify has 189 files, but the live sync upserts files one by one and never imports.
- **`--attachment` is literal (#9787, v0.8.0).** `--attachment a,b` is now one file named
  `a,b`. The bundle passes one path per flag
  (`autopilots/monthly-claude-code-insights.description.md:91`).
- **Daemon fixes with no setup change:** Claude control replies drained before stdin closes
  (#9721), Claude sessions resume across continued local worktrees (#9734), orphaned
  worktrees recovered after a cancelled `worktree add` (#9838), queued tasks follow a runtime
  switch (#9960), runtime probes run in an empty temp dir (#9957), and backslashes are kept in
  agent output (#9917).
- **`--until-pr reviewed` was reverted (#9839, reverted by #9862, v0.8.0).** `--until-pr` still
  offers only `checks|merged|conflicts`. It cannot serve the 2026-10-26 P2 pr-reviewer wait
  yet.
