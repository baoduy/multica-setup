# Multica release review — v0.4.40..v0.6.0 (2026-09-28)

Installed: multica 0.5.3 (CLI, daemon and self-hosted server, commit ff8b285).
Releases: v0.4.40 (2026-09-04), v0.4.41 (09-07), v0.4.42 (09-09), v0.4.43 (09-11),
v0.4.44 (09-15), v0.5.0 (09-18), v0.5.1 (09-21), v0.5.2 (09-23), v0.5.3 (09-24),
v0.6.0 (09-28). 380 changelog lines; about 170 PRs read in full.

Everything up to v0.5.3 is already live. Only the v0.6.0 items need an upgrade.

## Summary

1. **Live defect now.** `multica issue list --limit 200` has been rejected since
   v0.4.42 (#7896, limit 1–100). `architecture-review-sweep` uses it for dedupe in
   both bundles. The DKNet monthly review is next due in 2 days. (P1)
2. **v0.6.0 breaks the mx architecture-review roll-up.** The sub-issue-done wake is
   now a system wakeup rule and posts no "stage complete" comment (#8807). The mx
   arch-reviewer is told to wait for that comment. Fix it before upgrading. (P4)
3. **v0.6.0 PR-merge status setting (#8862).** The setting replaces the `Closes`
   keyword rule. If a workspace ends up on the default (`done`), merging a PR titled
   with the root `[KEY]` moves the root to done, which is exactly what Policy 03 §7
   guards against. Check the setting after upgrading. (P5)
4. **mx still keeps flow state in issue metadata.** Since v0.4.41 (#8102) the
   platform teaches agents that properties hold workflow state. drunk already moved
   (Policy 05 §9a). mx did not. (P2)
5. **Wakeup v2 (v0.6.0) conditions** (`--until-pr`, `--until-issue`) can replace
   two fragile patterns: the 30-minute foreground CI poll in `pr-review-gate`, and
   the member-mention handoff when a fix finishes above a blocked gate. (P6, P7)

## Proposals

### P1 Page the architecture-review dedupe list — breaks assumption (live now)
- Feature: `issue list` validates `--limit` to 1–100 and `--offset` ≥ 0, with a
  truthful `has_more` (#7896 in v0.4.42). Needs upgrade: no. It fails on 0.5.3
  today, checked: `--limit must be between 1 and 100 … use --offset to page`.
- Setup today: `drunk-workspace/skills/architecture-review-sweep/SKILL.md:84` and
  `mx-workspace/skills/architecture-review-sweep/SKILL.md:80` run
  `multica issue list --project <id> --limit 200 --output json` for the dedupe
  seen-set. Every run of that step errors. An agent that works around the error
  silently may dedupe against nothing and file duplicates.
- Change: `--limit 100` plus an `--offset` loop until `has_more` is false. Add
  `--fields` (v0.4.41 #7946) to fetch only title and identifier. Both bundles, then
  push the skill live.
- Policy impact: none (skill procedure).
- Benefit / risk / effort: stops a failing step before the Oct DKNet run / none / S.

### P2 mx: move flow state from issue metadata to custom properties — replace workaround
- Feature: #8102 (v0.4.41) removed all metadata guidance from the runtime brief and
  the built-in skill. The new rule reads: "workflow state a human should see and
  filter by goes in a property". `issue create --property Name=Value` (#8689,
  v0.5.2) and `--resolve-properties` (#8008) make properties cheap to set and read.
  Needs upgrade: no.
- Setup today: mx keeps state in metadata that is invisible on the board:
  `stuck_wake_count` and `blocker_nudge_count`
  (`mx-workspace/autopilots/hourly-stuck-run-recovery-…description.md:12,65,101`),
  `review_round/score/verdict` (`mx-workspace/skills/pr-review-gate/references/multica-flow.md:27-32`),
  `ship_required/bdd_required` (`mx-workspace/skills/sdlc-flow-po-orchestration/SKILL.md:67-68,123`),
  `arch_dispatch` (`mx-workspace/autopilots/monthly-architecture-review-…description.md:70`),
  `arch_*` (`mx-workspace/skills/architecture-review-sweep/SKILL.md:128-130`) and
  `bdd_*` (`mx-workspace/skills/bdd-review-sweep/SKILL.md:76,88`).
  drunk made this move already: `Wake count`, `Gate verdict/round/score`,
  `Arch fingerprint` (`drunk-workspace/workspace/workspace.context.md:22-23`).
  drunk has one leftover: `drunk-workspace/skills/multica-brainstorming/SKILL.md:44`
  still reads `issue metadata list`.
- Change: in mx, create the properties that mirror drunk's (`Wake count`, `Gate *`,
  `Arch fingerprint`, plus `Ship required`/`BDD required`) and cascade them to the
  autopilot, skills, agents and workspace context. In drunk, change the
  brainstorming read to `--resolve-properties`.
- Policy impact: mx has no counterpart to drunk Policy 05 §9a ("Gate state lives on
  custom properties"). Adding one amends mx policy 05 (or 04). **Needs owner
  approval.**
- Benefit / risk / effort: state is visible and filterable on the board, matches the
  platform brief and drunk / running cycles lose their counters mid-flight unless
  they are migrated at a quiet point / M.

### P3 Set properties atomically at create — new capability
- Feature: `multica issue create --property Name=Value` (repeatable) commits the
  issue and its properties in one transaction (#8689, v0.5.2). Needs upgrade: no.
- Setup today: `workspace.context.md` (drunk `:21`, mx `:26`) says to set `Owner` on
  every issue created, and the leader sets `Retrigger on done` on fix sub-tasks
  (`drunk-workspace/workspace/workspace.context.md:24`, mx leader playbook `:55,70`).
  Both are separate `property set` calls after `issue create`. A turn that dies in
  between leaves an issue with no Owner. This is one of the "runs stop without
  failing" shapes.
- Change: fold `--property "Owner=…"` (and `Retrigger on done` for a fix filed
  above a blocked gate) into the create command in the leader playbooks and the
  workspace context of both bundles. Keep `property set` for later appends.
- Policy impact: none (the rule is unchanged; only the command changes).
- Benefit / risk / effort: no ownerless children and one fewer call per create /
  low / S.

### P4 mx arch-review roll-up must not wait for a "stage complete" comment — breaks assumption (on upgrade)
- Feature: in v0.6.0 the sub-issue-done wake is an ordinary `issue_wakeup` row
  (`system_rule`, `child_done`). It posts **no system comment**. The run carries a
  `[WAKEUP]` block with stage counts, plus a `wakeup_triggered` timeline entry
  (#8807). Needs upgrade: yes.
- Setup today: `mx-workspace/agents/arch-reviewer.md:40` ("Woken … by 'stage
  complete' comment") and
  `mx-workspace/autopilots/monthly-architecture-review-monxa-backend-services.description.md:72`
  ("wakes you … with the 'stage complete' comment"). After the upgrade that comment
  never appears, so a literal agent will not recognise its roll-up wake.
- Change: reword both lines to "on the sub-issue-done wake (all four `[RP#]`
  terminal — check with `multica issue children`)". The wording should not depend on
  a comment or a `[WAKEUP]` block, so it works before and after the upgrade. Push
  live **before** upgrading the server. drunk has no equivalent: its orchestration
  text says "stage-complete wake" and reads children
  (`drunk-workspace/skills/sdlc-flow-po-orchestration/SKILL.md:72`).
- Policy impact: none.
- Benefit / risk / effort: the monthly mx roll-up keeps working / none / S.

### P5 Pin "After PRs merge" to *Don't change*; refresh Policy 03 §7's rationale — breaks assumption (on upgrade)
- Feature: `settings.pr_merge_status` replaces `pr_auto_complete_enabled` and the
  close-keyword rule. When every PR linked to an issue merges, the issue moves to
  the chosen status. Linking works by title, branch or body `Closes`. Migration 551
  pins `none` only on workspaces whose history shows non-keyword merges. A workspace
  with no PR links keeps the `done` default (#8862, v0.6.0). Needs upgrade: yes.
- Setup today: PR titles carry the ROOT key `[KEY]`, and `Closes`/`Fixes`/`Resolves`
  are banned because "close intent auto-completes the ticket and kills the remaining
  phases" (`drunk-workspace/docs/policies/03-source-control-branching.md:64`,
  `mx-workspace/docs/policies/03-source-control-branching.md:62`,
  `drunk-workspace/workspace/workspace.context.md:29`, both `leader-gitops/SKILL.md:25`,
  both `release-manager.md`). Under v0.6.0 the feature PR merging into `dev` would
  move the root to `done` if the setting is on `done`. The keyword ban no longer
  protects anything.
- Change: right after the upgrade, read Settings → Integrations → GitHub (or
  self-hosted Git) → "After PRs merge, move the issue to" in both workspaces and set
  **Don't change**. Then amend the rationale in Policy 03 §7 and in every copy of it
  listed above: the protection is now the workspace setting. The keyword ban can stay
  as belt and braces.
- Policy impact: Policy 03 §7 in both bundles (the rationale changes, the rule
  stays). **Needs owner approval.**
- Benefit / risk / effort: a merged feature PR cannot close a root mid-pipeline /
  none / S.

### P6 pr-reviewer: wait for CI with a wakeup instead of a 30-minute foreground poll — new capability
- Feature: `multica issue wakeup create <issue> --agent-id <self> --until-pr checks`
  (`pull_request: checks_finished`; `merged` is also available), with
  `--expires-in` and `--on-timeout wake`. It wakes the agent once checks finish, and
  CI that finished before the rule was registered is ignored (#8807, v0.6.0). Needs
  upgrade: yes.
- Setup today: `drunk-workspace/skills/pr-review-gate/SKILL.md:81` polls
  `gh pr checks` in the foreground every ~2 minutes for up to 30 minutes
  (`references/github.md:37`). mx works the same way. Long turns are where Claude
  runs stall (memory: runs stop without failing; the auto-background issue in
  DRK-1673).
- Change: when CI is still running, pin gate state on the properties (`Gate round`
  already exists; `.pr-review/<PR>/` does not survive a fresh checkout), create the
  wakeup with `--expires-in 30m --on-timeout wake`, and end the turn. On the wake,
  re-collect and merge on score as today. Both bundles.
- Policy impact: none found. Policy 04 in neither bundle states the CI wait; it
  lives in the skill only.
- Benefit / risk / effort: shorter reviewer turns and no idle 30-minute runs / one
  extra run per slow-CI PR and a new code path / M. Pilot in drunk.

### P7 Fix-above-a-blocked-gate: wake the leader with `--until-issue` instead of a member mention — replace workaround
- Feature: an `other_issue` condition, `--until-issue <KEY> --until-issue-state done`.
  Runaway protection comes from `max_fires` and the `loop`/`rate` pauses.
  "Acknowledged" suppression means an agent's own changes never wake it (#8807,
  v0.6.0). Needs upgrade: yes.
- Setup today: a `done` above a `blocked` stage fires no barrier. The workaround is
  that the member must notice this and end its report with the leader's mention
  (`drunk-workspace/skills/sdlc-flow-squad-worker-playbook/SKILL.md:9`,
  `…/references/recovery.md:18`). The leader then scans `Retrigger on done` on every
  wake and has a "your re-arm was lost" stall check (`recovery.md:14`). The mx
  leader playbook repeats the pattern (`:9,55,70,103-104`).
- Change (pilot in drunk dev-team): when the leader files or re-arms a fix above a
  blocked gate, it also creates one wakeup rule on the cycle parent targeting
  itself, one per fix key. The member's "mention the leader when your done closes no
  barrier" rule is removed. `Retrigger on done` stays as the record of which gate to
  re-arm; retiring it is a later step once the pilot holds.
- Policy impact: drunk Policy 05 §5 (stage barriers and mention handoffs) and the
  "One wake per handoff" list of enqueue sources in `workspace.context.md` (drunk
  `:10`, mx `:17`) gain a new wake source. **Needs owner approval.**
- Benefit / risk / effort: removes the handoff members most often get wrong / wakeup
  rules are new and only trusted after a pilot / M–L.

## Breaking or behaviour changes to verify

- **Upgrade order for v0.6.0:** migrations 548–560 → server → daemon. Merged
  wakeups need a daemon that advertises `joined-wakeups-v1`. Before that, a
  wakeup queues its own run as before.
- **Sub-issue wake semantics (v0.6.0):** a child closed outside HTTP (for example
  marked duplicate) now wakes the parent. A parent parked in `backlog` holds its wake
  until it leaves backlog. The final wake of a staged parent now also waits for
  unstaged children. drunk stages every child (`workspace.context.md:19`). mx arch
  review is deliberately all-unstaged, so it still fires once. Duplicate wakes
  caused by a barrier racing a mention (DRK-1282) should merge; watch the first
  cycles.
- **`multica agent tasks` returns the newest 200 (v0.6.0 #8804)**, with a cursor on
  stderr. Both run-recovery scripts
  (`drunk-workspace/autopilots/hourly-run-recovery.description.md:35,56`,
  `mx-workspace/autopilots/hourly-stuck-run-recovery-…description.md:25`) take the
  newest task per issue, which is still correct. Their text says "full task history".
  Check that the stderr continuation line does not trip the `|| echo SWEEP PARTIAL`
  guard.
- **Telemetry:** self-hosted servers have sent daily anonymous telemetry by default
  since v0.4.44 (#8252). `DO_NOT_TRACK` is not set on `multica-backend`. Owner to
  decide.
- **Editing a comment re-enqueues every agent it mentions** (#8548, v0.5.0). No
  bundle uses `issue comment update` today. Keep it that way, or restate the
  mention-wake rule if one ever does.
- **Cancelled ≠ done in stage progress** (#8495, v0.5.0). The `Retrigger on done`
  re-arm waits until "every child naming that key is `done`". A cancelled naming
  child then blocks the re-arm forever. Consider "`done` or `cancelled`" in both
  bundles' wording.
- **`--no-start` is gone from the runtime brief** (#8680, v0.5.2). Both workspace
  contexts carry it inline (`drunk-workspace/workspace/workspace.context.md:8,24`),
  so nothing breaks. This confirms that inline wording is the only thing agents
  follow.
- **Thread-scoped run queueing** (#8131, v0.4.42): separate root comments that
  mention the same agent get separate runs. The existing rule "at most one mention
  comment per turn" is what prevents duplicates. Keep it.
- **Autopilot triggers from before v0.4.39** were silently skipped until the #8293
  backfill. The drunk `multica autopilot list` shows `LAST_STATUS completed` for
  all 7. mx has not been checked.

## Not adopted (relevant but not useful here)

- Human steering of a running agent (#8682, #8760): a composer feature for people,
  not agents.
- Wakeup check-ins: they exist only for every/cron wakeup rules. The autopilots are
  not wakeup rules.
- Wakeup v1 (v0.5.1, installed): superseded by v0.6.0 conditions. Adopt at P6/P7
  rather than twice.
- Triage state (#8373): behind the `TriageV1` flag, off by default, no intake UI.
- Mark as duplicate (#8691 and follow-ups): UI only. The hygiene autopilots already
  treat `cancelled` generically.
- Agent-triggered autopilots (#8099/#8107): no agent triggers an autopilot.
- Consolidated `multica-platform` built-in skill (#7968): no bundle names the old
  skills.
- Runtime fixes for Codex, Cursor, OpenCode, Pi/OMP, Hermes, Grok, OpenClaw,
  CodeBuddy and Antigravity: every agent in both bundles runs a Claude model.
- Model catalog additions (#8840 Opus 5.5 and others): already in use.
- `--conversation-starters` (#8225): chat empty state only.
- Healthy WS claim poll relaxed to about 3 minutes (#7983): idle pickup can take up
  to about 2m45s. Set `ws_claim_poll_interval` only if that latency hurts.
