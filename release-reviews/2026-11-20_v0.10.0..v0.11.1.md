## Summary

1. **The owner no longer hears about a blog root parked `in_review` (#10778, v0.11.0).**
   Status-change notifications are now muted by default for every member who has not stored
   `all`. blog-team hands its root to the owner with a status flip and no mention
   (`squads/blog-team.md:38`). The owner is a passive subscriber, so that handoff now leaves
   no inbox item. dev-team's equivalent handoff already carries the owner's mention
   (`skills/sdlc-flow-squad-leader-playbook/SKILL.md:68`). P1.
2. **archify is 28 KB from the new per-file skill limit (#10761, v0.11.0).** Skill file
   writes now fail with HTTP 413 above 1 MiB per file, above 512 supporting files, or above
   8 MiB of supporting files in total. `skills/archify/renderers/shared/generated-validators.mjs`
   is 1,020,040 B against a cap of 1,048,576 B. The next archify sync that grows it fails at
   `multica skill files upsert`, and that happens during a live push. P2: add a lint rule.
3. **Inline CLI text is no longer escape-decoded (#10526, v0.10.0, BREAKING upstream).**
   `--content`, `--description`, `--instruction` and `workspace update --context` now keep
   `\n`, `\t` and `\\` as literal characters. No damage was found. There were 0 literal `\n`
   in 24 recent comments and 60 issue descriptions, and no bundle text tells agents to write
   inline escapes. But the live-sync guard (`scripts/drunk-live-sync.py:171-172`) and
   `README.md:3` still describe the old decoding. P3.
4. **Autopilots can now be assigned to a squad (#10709, v0.11.0).** In the same release, an
   explicit mention of the leader runs as a leader task (#8918). Both monthly upgrade autopilots
   assign dev-leader as a plain agent. They then ask it to "run your normal squad cycle", whose
   step 6 is `multica squad activity`. That command works only in a leader task. P4.
5. **An issue write now says why it started no run (#10858, v0.11.0).** `issue assign`,
   `issue status` and `issue update` print `No run started: … (<reason_code>)` on stderr. This
   is direct evidence for the leader's actuation check (`sdlc-flow-squad-leader-playbook/SKILL.md:24`),
   which today infers a stall after the fact. P5.

Open owner items carried forward, still undecided: Rule B deletion (2026-11-09 P1, updated
2026-11-16; `autopilots/weekly-issues-hygiene-cleanup.description.md:17` still says
"Deletion has no CLI command"), and PR auto-complete as the real guard (2026-11-16 P2).

## Proposals

### P1 blog-team's `in_review` handoff needs the owner's mention — breaks assumption
- Feature: the `status_changes` notification group defaults to muted for members without an
  explicit `all` (#10778, v0.11.0). Before that, #10688 (v0.10.0) cut passive subscriptions on
  other people's issues to `key_updates`: mentions, replies in your own thread, and handoff
  status changes. Mentions are always delivered. The agent's result comment is delivered to the
  human only on directly human-triggered runs (#10656), not on autopilot or webhook chains.
  Needs upgrade: no.
- Setup today: `squads/blog-team.md:38` finalizes the root `in_review` "for its human owner"
  with the PR URL and `Deploy: develop→main pending`, and no mention. The ticket is assigned
  to the blog-team squad, so the owner is a passive subscriber. That status flip was the only
  signal. The dev-team root handoff already adds "a member mention of the resolved owner"
  (`skills/sdlc-flow-squad-leader-playbook/SKILL.md:68`). Every other `in_review` in the
  bundle is either forbidden (`workspace/workspace.context.md:7`) or comes with a mention.
- Change, owner's choice: (a) add "and a member mention of the resolved owner" to
  `squads/blog-team.md:38`, matching the dev-team line; or (b) set Settings → Notifications →
  status changes to All on the owner account and change nothing in the bundle. (a) holds for
  any other human owner too.
- Policy impact: none. No policy quotes the blog-team handoff line (`grep "Deploy:
  develop"` hits only `squads/blog-team.md`).
- Benefit / risk / effort: a finished blog post stops waiting unseen / one more mention per
  blog cycle / S.

### P2 Lint the skill size limits before a push hits HTTP 413 — breaks assumption, latent
- Feature: manual skill create, update and file writes enforce 1 MiB of UTF-8 per file
  (`SKILL.md` limited separately), at most 512 supporting files, and at most 8 MiB of
  supporting files in total (`SKILL.md` not counted). An oversized write returns HTTP 413
  (#10761, v0.11.0). Needs upgrade: no.
- Setup today: archify has 188 supporting files and 5,308,088 B in total. Its largest file is
  `renderers/shared/generated-validators.mjs` at 1,020,040 B, which leaves 28,536 B of
  headroom. Every other bundle skill is far below the limits. The lint in
  `scripts/drunk-live-sync.py` (L1–L11) checks NUL bytes (L11) but not size. The archify sync
  procedure in the setup repo's `CLAUDE.md` names L11 as the merge blocker.
- Change: add L12 to the lint. It fails when a skill file exceeds 1,048,576 B, when a skill
  has more than 512 supporting files, or when its supporting files exceed 8,388,608 B. Name L12
  next to L11 in the `CLAUDE.md` archify section. If a later archify release crosses the cap,
  the fix belongs upstream (split the generated file) or in a bundle-side split. That is an
  owner decision when it happens.
- Policy impact: none.
- Benefit / risk / effort: the archify bump PR fails in CI instead of halfway through a
  live push / none / S.

### P3 Inline text is literal now: drop the backslash guard and fix the README — breaks assumption
- Feature: the CLI returns inline text unchanged (#10526, v0.10.0). This covers
  `issue create|update --description`, `issue comment add|update --content`,
  `issue wakeup create|update --instruction`, `user profile update --description` and
  `workspace create|update --description|--context`. File and stdin input is unchanged: it is
  read literally, with one final LF trimmed. Agent, squad and autopilot
  `--instructions`/`--description` were never decoded and are not in the PR's table.
  Needs upgrade: no. The CLI on the daemon host is 0.11.1.
- Setup today: `scripts/drunk-live-sync.py:171-172` refuses to push a workspace context that
  holds a backslash, "--context would decode it". `README.md:3` says "`--context` decodes
  backslash escapes". Neither is true on CLI ≥ 0.10.0. No bundle file shows agents an inline
  `\n`. A sample found no damage: 0 literal `\n` in the 24 comments on the 12 issues updated
  since 2026-11-16, and none in the 60 newest issue descriptions.
- Change: delete the guard, keep raw-argv `--context`, and reword the README sentence:
  inline text is literal since CLI 0.10.0, and `--context-stdin` still drops the trailing
  newline. The owner's auto-memory note on byte-exact pushes is corrected in this session.
- Policy impact: none.
- Benefit / risk / effort: the workspace context can hold a Windows path or a regex /
  wrong only if a host runs a CLI older than 0.10.0 / S.

### P4 Assign the monthly upgrade autopilots to dev-team, not dev-leader — new capability
- Feature: `multica autopilot create|update --squad <name-or-id>` / `--squad-id <uuid>`,
  mutually exclusive with `--agent` (#10709, v0.11.0). The run issue is assigned to the squad,
  so the leader runs it as a leader task. Separately, #8918 makes an explicit leader mention on
  a squad-assigned issue a leader task as well. Needs upgrade: no.
- Setup today: `autopilots/monthly-nuget-upgrade-dknet.json` and
  `autopilots/monthly-npm-upgrade-pulumi-repos.json` set `assignee_type: agent`,
  `assignee_name: dev-leader`. Both are `paused`. The NuGet prompt says "run your normal squad
  cycle … per your playbook" (`.description.md:10`). The playbook's step 6 is
  `multica squad activity <cycle-parent-id>` (`skills/sdlc-flow-squad-leader-playbook/SKILL.md:23`),
  which returns 400 "not a squad leader task" outside a leader task. dev-leader leads both
  dev-team and blog-team, so a plain agent assignment also leaves the squad unnamed.
- Change: set both autopilots to `assignee_type: squad`, `assignee_name: dev-team`. Let lint
  L6 accept a squad from `manifest.json`. Switch the live assignee by hand
  (`multica autopilot update <id> --squad dev-team`); the sync script does not push autopilot
  config. Do this before either autopilot is resumed. Verify it with one manual run.
- Policy impact: none found. No policy names these autopilots' assignee.
- Benefit / risk / effort: the upgrade cycles record squad activity like every other cycle /
  untested until the next resume / S.

### P5 Use the "No run started" line in the actuation check — new capability
- Feature: `PUT /api/issues/{id}` and the batch update return
  `run_outcome {target_type, target_id, status, reason_code}` when the write could start a run.
  The CLI's `issue assign|status|update` prints one stderr line when none started, e.g.
  `No run started: the issue is in Triage; accept it first (issue_in_triage).` The reason
  codes are `queued`, `coalesced`, `deferred` (`already_active`) and `blocked`
  (`issue_in_triage`, `agent_runtime_required`, `target_unavailable`, `attribution_blocked`,
  `project_access_blocked`, `internal_error`). From #10858 in v0.11.0. Needs upgrade: no.
- Setup today: the leader's actuation check (`sdlc-flow-squad-leader-playbook/SKILL.md:24`)
  asks whether each decision woke its executor. product-owner's promotions
  (`sdlc-flow-po-orchestration/SKILL.md:57`, `references/bundle-root.md`) and the leader's
  step 2 promotions (`:19`) assume the status flip is the wake. A promotion that started no run
  is found only by the daily stall sweep, 24 h later
  (`autopilots/daily-stall-sweep.description.md:13`).
- Change: one sentence in the actuation check, plus the same clause after the PO promotion
  step. A `No run started: … (blocked/<code>)` line on a promotion or assignment means the
  executor did not wake: fix it (accept the triage issue) or escalate per
  `references/recovery.md`. `queued`, `coalesced` and `deferred` are fine.
- Policy impact: none. This adds evidence to an existing check and changes no rule.
- Benefit / risk / effort: a dead promotion is caught in the same run, not a day later /
  a few words of context per leader run / S.

## Breaking or behaviour changes to verify

- **Same-issue self-mentions are suppressed (#10765, v0.11.0).** An agent's own mention on
  the issue it is running on no longer queues a run (`blocked/self_trigger_suppressed`). A grep
  found no bundle flow that relies on waking itself. Cross-issue self-mentions still dispatch.
- **Worker comments that mention a human now wake the squad leader (#10760, v0.11.0).** The
  echo rule (`sdlc-flow-squad-leader-playbook/SKILL.md:14`) ends those runs when the author's
  run is still active or the sub-task is terminal. Expect a few more short leader runs.
- **`@squad` mentions no longer notify squad members (#10794).** An explicit mention of the
  leader on a squad-assigned issue is a leader task (#8918). Both match how the bundle routes.
- **Retries follow the agent's current runtime (#10788, #10801, #10859).** A retry used to
  copy the parent's runtime and could strand on a runtime no daemon claims, as when the Codex
  runtime moved (auto-memory `codex-runtime-cli-path`). hourly-run-recovery wakes by comment,
  not by retry, so it changes no step. Watch its "stranded queued" cases disappear.
- **Stale empty-claim stall fixed (#7824).** Woken runtimes force a server re-check. Daemon
  and server are both 0.11.1. Tasks should no longer sit up to 3 min after enqueue.
- **NUL bytes are stripped from issue, project and doc text (#10944, #10936).** Skill files
  are not covered, so L11 and archify's `\u0000` escapes stay.
- **Archived projects reject new issues with `409 project_archived` and pause their
  autopilots (#10620).** No drunk project is archived. Archiving one later pauses its
  autopilots, and they do not resume by themselves.
- **`project list` / `GET /api/projects` return 400 on unknown filter or sort values (#10628).**
  No bundle text passes them.
- **Private projects now admit only their members, and admins no longer see them (#10618,
  #10723).** All six drunk projects are `visibility: workspace`.
- **Inbox reads by agent tokens are owner-gated (#10726, #10739, #10861, #10974).** No bundle
  file reads the inbox.
- **The runtime brief is `skip-worktree` during a run (#10787).** No bundle rule worked around
  agents committing `CLAUDE.md`/`AGENTS.md`.
- **Codex inactivity timer (#10906).** It matters only with `MULTICA_AGENT_IDLE_WATCHDOG=0`,
  which no agent's `custom_env` sets.

## Not adopted (relevant but not useful here)

- Chat wakeups (#10770, #10826, #10855, #10941): drunk's flow runs on issues, and issue wakeups
  already cover it.
- Docs (#10176, #10954, #10946, #10936): gated by `FF_DOCS_V1=true` on the server (`docs_v1`
  is false). This is undocumented and still "being tested". Turning it on is the owner's call.
  Docs-writer delivers to repos, which Policy governs, so Docs would be a new channel to design.
- `multica view create|update|duplicate|delete` (#10555): there are no shared views to keep.
- `multica issue batch update` (#10629): issue-janitor could flip statuses in one call with
  `--dry-run`, but Rule B comes first.
- Webhook payload conditions (#9485) and filter files (#10649): the only webhook autopilot is
  the live sync, fed by our own GitHub Action, which already filters on `main` and the bundle
  path.
- `issue pull-requests link|unlink` (#10593): phase PRs already link by branch and title.
- Runtime profile `--daemon-id` (#10746), project folders (#10817, ee), the skill slash menu and
  invocation (#10774, #10772, human-authored only), and webhook dedupe by delivery (#10559): no
  drunk use.
