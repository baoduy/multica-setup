# Multica release review — v0.12.0..v0.13.0 (2026-11-26)

Installed: multica 0.12.1 (CLI on this machine, commit fc8028d76, built 2026-11-23; both
runtimes on Stevens-Mac-mini report 0.12.1). **The server is on v0.13.0.** `/api/config` reports
`server_version: v0.13.0`, `issue_blockers_supported: true`, and the flags `docs_v1: false`,
`composio_mcp_apps: false`, `plugins_v1: false`, `project_workflows_v1: true`,
`workspace_guests: true`. So every server-side change below is live, and every change that
needs a 0.13.0 CLI or daemon is marked **needs upgrade**. Releases: v0.12.0 (2026-11-23),
v0.12.1 (2026-11-23), v0.13.0 (2026-11-25). 350 PRs in the changelogs. 213 were read in full
by four readers. The other 137 are listed under Skipped. Owner session, run together with a
review of the squads against https://multica.ai/docs/squads.

## Summary

1. **A later-stage sub-issue no longer starts while an earlier stage is open (#10279,
   v0.13.0).** Promotion out of `backlog` and creation at `todo` used to start a run whatever
   the stage. Now the platform holds the run until every earlier-stage sibling is closed, then
   starts it by itself. Three flows rely on the old behaviour: the bundle root promotes the
   next stage while this one builds, dev-leader files a `Fix:` sub-task above a `blocked`
   Review, and dev-leader files a scope stage "that can run now". The first loses its
   pipelining. The other two can stall, because the Review waits for the fix and the fix now
   waits for the Review. Not yet seen live: no cycle has run since the server moved to
   v0.13.0 (P1).
2. **The same rule now wakes a waiting sub-task by itself when a re-armed earlier stage closes
   again (#10279).** After a rework, the Build's second `done` should start pr-reviewer on the
   `blocked` Review without dev-leader's re-arm. dev-leader's re-arm then arrives as a second
   wake. Verify on the next REWORK (P2).
3. **The weekly hygiene sweep still deletes nothing.** Rule B has returned HTTP 403 on every
   run since 2026-11-08, most recently on 2026-11-22 and 2026-11-23. v0.12.0 adds a second reason to
   drop the REST call: `$MULTICA_TOKEN` is no longer guaranteed in a built-in Codex run's
   environment (#11217). This is the 2026-11-09 P1, still waiting for the owner (P3).
4. **Both runtimes and the CLI are one release behind the server.** v0.13.0 carries daemon
   fixes for the failure this workspace has: runs lost to a daemon restart. The Runtimes page
   can now queue the update until the machine is idle (#11034) (P4).
5. **Direct member handoff and member briefs (#11353, v0.13.0) do not fit this pipeline.**
   Both act only on a ticket assigned to the squad itself. Members here work on their own
   agent-assigned sub-tasks. Measured cost of the leader hop they would remove: about 1.5
   minutes per rework round, 5 rounds in 5 weeks. Not adopted.
6. **`multica issue edit-description` replaces part of a description without rewriting it
   (#11168, v0.12.0).** dev-leader edits two descriptions per cycle. Small, no policy impact (P5).

## Proposals

### P1 A later stage at `todo` waits for the earlier stage — breaks assumption

- Feature: issue blockers and stage blockers, from #10279 in v0.13.0 (follow-ups #11395,
  #11502, #11516). A sub-issue in a later stage lists every unfinished earlier-stage sibling
  as a blocker. The docs (`apps/docs/content/docs/issues.mdx`, "Blockers and waiting work")
  say: "While unfinished blockers remain, assigning an agent or squad (or moving the issue out
  of `backlog`) does not start a run. Direct @-mentions and comment replies still run." Once
  every blocker is closed the assignee starts automatically, unless the issue is in `backlog`.
  Before v0.13.0 stages grouped work and enforced no order. Needs upgrade: no, the server has
  it.
- Setup today:
  - `skills/sdlc-flow-po-orchestration/references/bundle-root.md:19` promotes the next stage's
    sub-issue to `todo` the moment this stage hands its `[P<num>-1]` to dev-team, and says "The
    promotion is the wake; post no mention." This stage's sub-issue is still `in_progress`, so
    the promoted one now waits until it is `done`. `:28` promotes "the stage after it" the same
    way. Specs no longer run one stage ahead (Policy 05 statement 1c,
    `docs/policies/05-sdlc-delivery-lifecycle.md:85`). The bundle still finishes, serially, and
    the root comment "Stage <n+1> promoted" is untrue until that stage closes.
  - `skills/sdlc-flow-squad-leader-playbook/references/review-outcomes.md:5` lets dev-leader
    file `[D<num>-n] Fix:` "at a stage above the gate". The gate is the Review sub-task, parked
    `blocked`, so it is an unfinished earlier stage. The Fix sub-task does not start. The
    Review waits for the fix. Nothing wakes anybody until `daily-stall-sweep` or a human.
  - `skills/sdlc-flow-squad-leader-playbook/SKILL.md:38`: "A scope sub-task that can run now
    is created `todo`", at the next unused stage number. With any lower stage still open it
    waits. `:48` adds "Create or promote to `todo` → no mention (redundant)", which is the rule
    that keeps all three silent.
  - `workspace/workspace.context.md:10` lists "assignment or promotion out of `backlog` into
    `todo`" as a wake with no condition.
- Change: state the new rule once in the Workspace Context wake list: a sub-issue above a
  stage that is still open does not start on assignment or promotion; it starts by itself when
  that stage closes, and an agent mention starts it at once. Then in the three places above,
  post ONE comment with the assignee's mention after creating or promoting such a sub-issue
  (product-owner mentions itself on the next bundle stage: a self-mention on another ticket is
  an explicit handoff and still runs). The default rework path, re-arming the existing Build,
  is not affected.
- Policy impact: Policy 05 statement 1c (the promotion alone no longer starts the next
  stage) and statement 5 with the Workspace Context wake list. **Needs owner approval.**
- Benefit: keeps the bundle's pipelining and removes two stall paths. Risk: when the earlier
  stage closes later, the platform's `blockers_done` rule may wake the same sub-issue once more
  (see P2); that run finds nothing to do. Effort: four text edits and a changelog entry.

### P2 `blockers_done` re-starts a waiting sub-task after a rework — behaviour change to verify

- Feature: the dependency wake from #10279. Source: `AcknowledgeIssueBlockerRelease` in
  `server/pkg/db/queries/issue_blocker.sql` releases any waiting issue whose status is not
  `backlog` and whose assignee is an agent or squad, and "A later wait resets condition_state
  and releases again". The run carries the system rule `blockers_done`. Needs upgrade: no.
- Setup today: on REWORK the Review sub-task sits `blocked` at stage 3. dev-leader flips the
  Build (stage 2) back to `in_progress`, so the Review gets an open stage blocker. When the
  Build goes `done` again, the stage barrier wakes dev-leader, who verifies the fix and re-arms
  the Review with `in_progress --no-start` and pr-reviewer's mention
  (`references/review-outcomes.md:8`; Policy 04 statement 10,
  `docs/policies/04-code-and-spec-review.md:67`). On v0.13.0 the platform should also start
  pr-reviewer on the Review at that same `done`, before dev-leader has verified anything. The
  same holds for `[P<num>-1c]` after a `[P<num>-1]` rework under product-owner.
- Change: none yet. On the next REWORK round, read
  `multica agent tasks <pr-reviewer-id> --limit 20 --output json` and look for a run on the
  Review sub-task with `wakeup_system_rule: blockers_done`. If it is there, the owner chooses:
  (a) keep the leader hop: pr-reviewer ends a `blockers_done` run at once, with no comment,
  while its Review is `blocked` and carries no re-arm comment; or (b) let the platform wake be
  the re-arm: dev-leader stops re-arming the Review and only acts when a fix report fails its
  check. (b) removes one leader hop per round and amends Policy 04 statement 10.
- Policy impact: none for the check. (a) adds a guard to `pr-review-gate` and
  `agents/pr-reviewer.md`. (b) amends Policy 04 statement 10. **Either needs owner approval.**
- Benefit: no double re-review. Risk: until it is settled, one rework round may run the gate
  twice. Effort: one check, then one edit.

### P3 Hygiene Rule B still returns 403 — breaks assumption (carried from 2026-11-09)

- Feature: #9789 (v0.8.1) lets an agent delete only the issues it created. New in this range:
  #11217 (v0.12.0) runs built-in Codex and Claude Code turns from a warm process pool, on by
  default. `MULTICA_TOKEN`, `MULTICA_TASK_ID`, `MULTICA_TASK_CONFIG_ROOT` and
  `MULTICA_TASK_SLOT` reach the `multica` CLI through a private per-turn file and "are not
  guaranteed to appear in the provider process environment or arbitrary child scripts"
  (`apps/docs/content/docs/daemon-runtimes.mdx`). Needs upgrade: no.
- Setup today: `autopilots/weekly-issues-hygiene-cleanup.description.md:17,28` and
  `agents/issue-janitor.md:19-20` call `DELETE /api/issues/<id>` with
  `Authorization: Bearer $MULTICA_TOKEN`. issue-janitor runs on the built-in Codex runtime.
  Runs of 2026-11-15, 11-16, 11-22 and 11-23 all stopped at the first DELETE with HTTP 403 on
  DRK-2473 and deleted nothing. No other bundle file reads a `MULTICA_*` task variable.
- Change: the owner's choice from the 2026-11-09 report is still open: (a) Rule B lists
  deletion candidates and the owner deletes them (`multica issue delete <id>... --yes`), or
  (b) retire Rule B. Both remove the REST call and the token handling.
- Policy impact: Policy 09 statement 1 and the issue-janitor charter. **Needs owner approval.**
- Benefit: the weekly report stops saying "partial". Risk: none. Effort: four files.

### P4 Upgrade the CLI and both runtimes to 0.13.0 with a queued update — operator action

- Feature: #11034 (v0.12.0) queues a runtime update until the machine is idle: Runtimes page,
  Update. It installs when no run is in flight, can be cancelled, and expires after 24 hours.
  `multica runtime update` from the CLI still fails at once on a busy machine. The 0.13.0
  daemon then brings #11524 (after a daemon restart a resumed Claude turn no longer takes the
  previous turn's result), #11449 and #11079. Needs upgrade: this is the upgrade; the daemon is
  already new enough to queue.
- Setup today: 4 of dev-backend's last 200 runs failed with "daemon restarted while task was
  in flight" or "daemon shut down while task was in flight". The 0.13.0 CLI is also what P1's
  alternatives and any later use of `--blocked-by`, `multica squad briefs` or
  `multica issue list --blocked` need.
- Change: none in the bundle. Update from the Runtimes page, then run `multica daemon status`
  on the Mac mini: since #11007 it names every skipped provider and the reason, which is the
  check for the Codex CLI path problem seen before.
- Policy impact: none.
- Benefit: fewer runs lost to restarts. Risk: the usual restart. Effort: minutes.

### P5 Edit part of a description with `multica issue edit-description` — new capability

- Feature: `multica issue edit-description <id> --old <text> --new <text>` (also `--old-file`,
  `--new-file`, `--replace-all`), from #11168 in v0.12.0. It replaces exact text in place and
  fails only when that text changed. The CLI help says to prefer it over
  `issue update --description*` for a partial change. Needs upgrade: no, CLI 0.12.1 has it.
- Setup today: dev-leader appends `at_sha` and the AT paths to the Build description
  (`squads/dev-team.md:40`) and fills the Review pointer table after it opens the PR (`:42-43`).
  Each is a full rewrite of a brief of several KB. In the last cycle (DRK-2592) the Build
  description changed twice and the Review description four times.
- Change: name the command in the two rows of `squads/dev-team.md` and in the matching steps
  of `sdlc-flow-squad-leader-playbook`. Try it on one ticket first: the live-merge part of the
  feature sits behind `issue_description_live`, which this server does not list.
- Policy impact: none. It changes a command, not a rule.
- Benefit: fewer output tokens per cycle and no overwrite of a concurrent edit. Risk: an
  `--old` text that is not unique fails, so the row to replace must be quoted whole. Effort:
  two files.

### P6 Owner inbox: mute squad handoffs, keep the final report — owner setting

- Feature: with **Include squad handoffs** off, the Inbox now still delivers the report a
  squad finishes with (#11416), and a squad called in with a squad mention counts as a handoff
  too (#11398), both v0.13.0. From v0.12.0: acting on an issue in a way that triggers an agent
  archives its notification by default (#11138, #11166), only forward status moves archive
  (#11156), and every notification opens on the Inbox page with Inbox, Snoozed and Archived
  tabs (#11259). Needs upgrade: no.
- Setup today: escalations reach the owner by reassignment plus a `## BLOCKER` comment
  (Policy 10). Nothing in the bundle depends on these settings.
- Change: none in the bundle. Settings, Notifications is the owner's call.
- Policy impact: none.

## Breaking or behaviour changes to verify

- **#10279 stage blockers and `blockers_done`.** P1 and P2. Unaffected paths, checked against
  the bundle: a first-pass Review and a `[P<num>-1c]` wait in `backlog` and are promoted after
  the earlier stage closed; `[P<num>-2]` on a bundle root is created `todo` when every child is
  closed; a re-arm is a mention, and mentions still run. `--no-start` is honoured when blockers
  end (#11502).
- **#10977 (v0.12.0) only a sub-issue closing wakes the parent's assignee.** Adding a
  sub-issue no longer fires `child_done`. That removes a double wake per stage when the leader
  creates the next stage dynamically. Trade-off from the PR: when every sub-issue is closed
  and a stage is added later, the parent's assignee is not woken. The bundle root's "further
  change" row (`references/bundle-root.md:31`) adds its stage at `backlog` and promotes it from
  another wake, so it is unaffected.
- **#11244 (v0.12.0) comment idempotency.** Inside an agent run the CLI derives a key from
  the run, issue, parent, content and attachments. A comment repeated with the same content on
  the same ticket in one run is posted once. No flow posts the same text twice, so no change.
- **#11217 (v0.12.0) warm session pool.** Besides P3: the model list is cached for 15 minutes
  instead of 60 seconds, and `MULTICA_WARM_POOL=0` on the daemon turns the pool off without a
  redeploy. `scripts/drunk-live-sync.py` uses the `multica` CLI only and reads no task
  variable.
- **#11391 (v0.13.0) a task token stops working when its task ends.** A process left running
  after the run can no longer write. This matches `workspace/workspace.context.md` ("Never run
  a long command in the background").
- **#10984 and #10994 (v0.12.0).** A task token lists only its own workspace and cannot delete
  a workspace. No bundle file calls `multica workspace list`.
- **#11143 (v0.12.0).** Multica tokens (`mat_`, `mul_`, `mdt_`, `mcn_`) are masked in stored
  and broadcast agent output. No change needed.
- **#9775, #11000 (v0.12.0), #11536 (v0.13.0) failure classes.** A per-minute token limit is
  now a retryable rate limit, not a context overflow. "Insufficient balance" is billing, not
  capacity. A safeguards refusal is `api_invalid_request`. No bundle file names these reasons,
  so `hourly-run-recovery` needs no edit.
- **#11492 (v0.13.0).** Two concurrent `multica issue update` calls on different fields no
  longer overwrite each other. This is the pattern agents use for status plus properties.
- **#11495, #11499, #11488 (v0.13.0).** The workspace settings form, the autopilot edit dialog
  and the skill editor no longer write stale values back. These were a source of the live
  edits the bundle had to record on 2026-11-23. The live sync still decides what live holds.
- **#11537, #11423, #11559 (v0.13.0) squad usage.** Recovery and system-wake runs now count
  toward a squad, and runs by agents outside the squad no longer do. Dashboard numbers for
  dev-team shift from 2026-11-25; earlier rows are not rewritten.
- **#11124 (v0.12.0) self-host Compose now passes documented backend variables.**
  `DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS`, `LOCAL_UPLOAD_BASE_URL`, `AUTH_TOKEN_TTL`,
  `RATE_LIMIT_TRUSTED_PROXIES`, `REALTIME_METRICS_TOKEN`, `REDIS_DISABLE_CLIENT_NAME` and
  `MULTICA_LARK_WS_PROXY_URL` were silently dropped before. A value sitting in the server's
  `.env` takes effect now. Not checked in this session; the owner reads that file.
- **#11055 (v0.12.0) rollback floor.** `workspace_guests` is on. Do not roll the server back
  below 0.12.x while a guest or a guest invitation exists.
- **#11252 (v0.12.1) and #11094 (v0.12.0) project workflow briefs.** They change the
  `[Project workflow]` block only. The 2026-11-16 report found that drunk projects use no project workflow; not re-checked.

## Not adopted (relevant but not useful here)

- **Direct member handoff and member briefs (#11353, #11532, v0.13.0).**
  `directSquadHandoffAuthor` and `squadMemberBriefingForClaim` both require the issue's
  assignee to be the squad. No member ran on a squad-assigned ticket in the sampled data.
  Evidence for the hop itself: 8 dev-team cycles since 2026-11-20 took 9.2 hours with no idle
  gap; developers used 75% of agent time, pr-reviewer 16%, dev-leader 10%. A stage wake is a
  median 54 seconds. Adopting it would amend Policy 04 statement 10 and Policy 05 statement 5
  for about 8 minutes saved in 5 weeks.
- **Manual blockers for the bundle build barrier (`--blocked-by`, #10279).** A
  `[P<num>-1]` could wait on the previous stage's `[P<num>-1]` instead of sitting in `backlog`.
  The barrier is "PR merged into `dev`" (`references/bundle-root.md:18`), which `done` alone
  does not prove, so product-owner's check would be lost. Needs upgrade as well.
- **`multica quick-action` CLI (#11326, #11336, v0.12.1).** Quick actions are saved prompts a
  member runs on an issue. The owner's replies here are a letter or "approved".
- **Skill writes with `--base-revision` (#11210, v0.12.0).** The live sync already reads each
  resource back and diffs it. It would guard a concurrent live edit; `scripts/` is the
  owner's to change.
- **Autopilot webhook payload conditions (#11374 docs, v0.13.0).** The `drunk-live-sync`
  trigger is called by one GitHub Action that already filters on the path.
- **Project progress and activity CLI (#10626, #10627, v0.12.0).** `multica project progress
  <id> --history --by assignee|label` and `project activity`. The weekly retro reads gate
  verdicts and failed runs, not throughput.
- **Guest role (#10766 and follow-ups, v0.12.0).** A free read-and-comment role scoped to
  shared projects. Available on this server. No one outside the owner uses the workspace.
- **Docs: comments, agent mentions, live co-editing, folder and history CLI (#10981, #11092,
  #11160, #11248, #11295).** All behind `docs_v1`, which is off. docs-writer and
  service-architect write to the repos.
- **Remote MCP apps and Composio (#11162, #11255, #10806, #11397).** Behind
  `composio_mcp_apps` and a new `MULTICA_APPS_SECRET_KEY`. Not used.
- **Collab service (#11122, #11168 live part).** Needs a new container and `COLLAB_SECRET`.
- **Steering for Antigravity and Hermes (#11200, #11315, #11419), Pi, Kimi, Reasonix, Trae,
  CodeArts, OpenCode and Cursor fixes.** No agent runs on these runtimes.
- **Daemon log level and rotation per profile (#11068, #11077) and the heartbeat log line
  (#11063).** `daemon.log` shrinks by itself after the upgrade.
- **Billing, seats, storage and history limits (#10957, #11035, #11042, #11044, #11032,
  #10876).** Cloud gates. A self-hosted server is never gated.
- **Model pricing (#11481, #11211).** No agent runs on Fable 5.2 or an Antigravity model.
